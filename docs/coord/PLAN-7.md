## 2. Principles
V1. THE VERSION IS A FACT, NOT A GUESS: show what the workspace really runs (read `claude --version` inside it, cached with a time), next to what it is pinned to (the image label) and say when they differ. Unknown is shown as unknown.
V2. PINNED MEANS PINNED: an exact x.y.z (no ranges, no latest) in the build arg and in the image tag and label; auto-update off in the image AND in the managed settings, and a check proves it (the canary asserts the version is unchanged after a run).
V3. UPGRADE IS EXPLICIT AND SAFE: a person picks the target version; a canary runs FIRST on a throwaway container from the candidate image (the stand-in Anthropic API and the existing testkits plus the REAL CLI: version, a stream-json turn the portal can parse, `claude mcp list` with a plugin-delivered stand-in server, the managed-settings drop-ins, `get_usage` and `rate_limit_event` handling, the session host cp-session, the MCP OAuth stand-in where cheap); each check reports pass, fail or skipped with the real output; only a green canary offers "Apply". Apply recreates the workspace's container from the new tag KEEPING its home volume, after a confirm that names running sessions; nothing is applied to a workspace without that action.
V4. ROLLBACK IS ONE ACTION: previous tags are kept (a small history per workspace: from, to, when, canary result); Rollback recreates from the previous tag; pruning old images is explicit and never removes a tag a workspace uses.
V5. MINIMUM VERSION PER FEATURE comes from ONE registry shared by server and web (packages/contracts), absorbing the scattered constants (keep their exports working), each entry naming the feature, the minimum, why, and how it was verified (observed on the real CLI, or documented). Below the minimum the feature degrades the way it already does (for example `claude_too_old`) and the UI says which feature and which version is needed.
V6. NO COLLISIONS: edit files other agents own only surgically and after re-reading; list every such edit in the report.
