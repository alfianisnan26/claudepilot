## 0. The owner's ask (2026-10-12, translated from Indonesian)
Add a "btw" (side question) feature to the session chat, like /btw in Claude Code. Check the composer (Steer and queue, slash commands if any), the turn flow, the session context and the desktop and phone chat layout first; EXTEND, do not rebuild.
FUNCTION
- Trigger: type `/btw <question>` (command suggestions when you type "/") or an icon button in the composer's button row (tooltip "btw"; icon only on a phone).
- The answer comes from a SEPARATE Claude instance that sees the session's context up to that moment, WITHOUT tools, ONE answer. It does not disturb a running turn, does not change the session's state, does not add to the main session's history.
- A temporary card that can be closed, with "Pin to transcript". A follow-up question is a new btw. Usable while the agent is working.
- Quota and cost are marked as estimates; a rate limit per session; if the quota is exhausted or there is an error, show the reason.
- FIRST test whether the real CLI supports /btw in the stream-json mode the portal uses. If yes, use it and show its result. If not, build it ourselves with a separate no-tools call with the same session context. Record the test result in the PRD.
LAYOUT (never a second permanent chat column)
- Wide desktop (>= about 1280 px): the card sits above the composer inside the same chat column, height limited, scrolling on its own; an "expand to side panel" button (resizable, closable, the choice remembered per device), offered only when the width allows, otherwise it returns to the card by itself.
- Tablet and narrow desktop: only the card above the composer.
- Phone: a half-height bottom sheet that can be dragged to full height, keyboard-aware, closed by swiping down or Esc. No second column.
- The card must not change the main transcript's scroll or disturb its auto-scroll while the agent writes. Content: a one-line question, the answer, Close / Pin / Ask again. Long explanations in an InfoTip.
- Accessibility: focus goes to the card, then back to the composer when it closes; the answer in a polite aria-live region; Esc closes.
SECURITY: the context goes through the same redaction as the chat; the answer cannot trigger an action or a tool; transcript text is untrusted.
TESTING: size matrix 390 (phone portrait), phone landscape, 768, 1024, 1280, 1920; light and dark; reduced motion. Conditions: the main turn streaming (the scroll must not jump), a very long answer, quota exhausted or an error, a cancel half-way, repeated btw in quick succession, the side panel resized and closed, the main transcript unchanged. Automatic checks: no horizontal scroll, the composer never covered by the card or the keyboard, a stable transcript scroll position. Look at a screenshot at every size. Add iOS Safari (keyboard, sheet) to the real-device checklist.
Rules: multiple agents, no collisions with running work, short UI (titles of 1-2 words, InfoTip), update the PRD, verify in a browser.

## 2. Principles
W1. NO TOOLS, NO ACTIONS, NO SIDE EFFECTS: the separate instance runs with every tool disabled (verified: the run's init message lists none, and a prompt asking it to run a command shows it cannot), one answer, no stored session of its own that the Sessions list or Claude Code's resume picker could show, nothing written into the main session (unless the person pins), and the answer is displayed as plain text or the safe markdown the chat already renders.

W5. LAYOUT RULES ARE TESTED, NOT HOPED: the matrix and conditions in section 0 become automatic checks (no horizontal scroll, composer not covered, stable scroll position) plus screenshots looked at.
