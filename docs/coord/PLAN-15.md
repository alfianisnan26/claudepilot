## 2. Principles
S1. SERVER = ORCHESTRATION AND TRUST: identity, permissions, policy, scheduling, audit, secrets and the cross-workspace INDEX stay in the server DB. WORKSPACE = PROJECT DATA: content that belongs to the project, that must travel with it, that is only useful with it, or that is large.
S2. WORKSPACE-RESIDENT DATA PATTERN (the first application is annotations/evidence): source of truth = files in a portal data folder inside the home volume (not in the project tree), written by the portal, with a FORMAT VERSION; the server holds a REBUILDABLE index; a stable workspace id stored INSIDE the workspace lets a re-attached workspace rebuild its index; reloaded content is validated (schema, sizes, paths, encodings) and treated as UNTRUSTED; per-user private data stays on the server; integrity (hashes recorded at write time) is only meaningful while attached, and "append-only for agents" can only be enforced at the API, never on files the agent controls: say so.
S3. LIFECYCLE IS EXPLICIT: "Detach from portal" (the portal forgets the workspace and drops its index; the volume and data stay) versus "Delete" (the volume is destroyed); unreachable workspaces keep their index but mark workspace-resident data unavailable; a re-attach test proves the rebuild.
S4. NUMBERS ARE MEASURED: size, WAL and growth come from real measurement with the method stated; the owner's real database is OFF LIMITS to agents: use scratch databases loaded with realistic synthetic volumes (state the load model) and provide a READ-ONLY measuring script (tools/qa/ or tools/) that prints table names, row counts, page sizes (dbstat) and WAL size only, never row content, which the OWNER can run on their own database; mark everything about the real database "not measured here".
S5. EVERY NEW FEATURE DECLARES ITS STORAGE: where, expected size and write rate, retention, rebuildability, trust level, what happens on workspace delete, detach and unreachable, and backup inclusion; enforced by a checklist in the PRD template and a test that fails when a table is not in the storage register.
S6. NO MIGRATION IN THIS ROUND: a plan with priorities, dry-run ideas, reversibility, backup impact and rollback; the work itself is later and staged.
S7. EXTEND, DO NOT REBUILD; NO COLLISIONS; multi-user and Connect compatibility are inputs, not afterthoughts.
