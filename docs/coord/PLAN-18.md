Put the extension OUTSIDE the globs (for example tools/vscode/ with its own package.json and lockfile, built by its own scripts) and keep server additions in new files under apps/server/src/vscode/.
- Test capacity: Chromium at /usr/bin/chromium, the portal's own browser pool (agentic MCP) for driving a web VS Code, @vscode/test-web (headless Chromium) feasible, @vscode/test-electron needs xvfb and an Electron download (arm64 Linux: check), the claude.ai "Desktop Coder MCP" (a remote Linux desktop) exists as an optional complement: use it only with care (the owner's own workstation, scratch directories only, no secrets, state exactly what you did).
- The machine is shared and memory-tight: ONE heavy process at a time; measure memory and startup of each option and record the environment.

## 2. Principles
VC1. EVIDENCE OVER OPINION: every option is TRIED here as far as the sandbox allows (install, start, connect, measure: memory, startup time, install size) and what cannot be tried (a real VS Code desktop client, Microsoft services, a Marketplace account) is marked UNVERIFIED with a manual checklist; licence terms are read, not assumed (the VS Code Server and `code tunnel` terms, the Microsoft Marketplace terms vs Open VSX, code-server and openvscode-server licences).
VC2. THE OPTIONS, each judged on: editor, language server, terminal, debug (what really works), cost (CPU, memory, disk, startup), security risk (what an attacker with that path gets), Connect target support (docker cluster, kubernetes, single host; unreachable targets), multi-user fit (user-bound access, per-workspace rights), and effort. (a) Remote-SSH through Connect: needs sshd in the workspace and an `ssh` stream or a portal ProxyCommand: try with a local ssh client, sshd in a workspace container and THROWAWAY keys; (b) attach to container: needs Docker access from the client: assess through Connect's docker stream and plain Docker; (c) `code tunnel`: Microsoft's service and login; record the terms and why it probably does not fit a self-hosted portal; (d) code-server/openvscode-server in the workspace through an authenticated portal proxy (HTTP and WebSocket, cookie or token, Origin checks, CSP): install in a workspace container, proxy through a stand-in route, drive with the agentic browser, check the extension host and Open VSX; (e) a virtual workspace through a FileSystemProvider in an extension: files from the portal's Files API, terminal from the portal's terminal socket, no remote extension host: what language features survive; try with @vscode/test-web.
VC3. THE EXTENSION uses STABLE API only (proposed APIs listed and avoided), works in desktop AND web hosts (a browser-compatible entry: no Node-only APIs there), and consists of: TreeViews (Workspaces, Sessions, Agents, Tickets), a WebviewView for the session/chat, commands and menus, a status bar (quota from the usage engine, needs-attention from the glance snapshot), terminals (a Pseudoterminal over the portal terminal), the session diff (a `claudepilot:` virtual document scheme and the diff editor), notifications and approvals.
VC4. SECURITY: tokens only in SecretStorage; login by device flow (a portal endpoint issues a USER-BOUND, REVOCABLE, minimally scoped token after the person approves a code in the portal) or by the URI handler; bearer-token auth (the extension has no cookie, so the CSRF/Origin model differs: say how the portal treats these requests); strict webview CSP (nonce, no remote scripts), everything from a workspace rendered as plain text, no secret in any output channel or log, approvals show the FULL text and never offer Allow for a cut request (the same rule as the web, see the approval-detail fix of U4), an extension-portal VERSION COMPATIBILITY check (a compat endpoint; refuse or degrade with a clear message), and the multi-user rules (the token never exceeds its owner's rights at use time).
VC5. TESTING: the web extension inside openvscode-server or code-server driven by the portal's agentic browser MCP against a FAKE PORTAL and a FAKE CLAUDE (the stand-in Anthropic API), deterministic; @vscode/test-web and, if feasible, @vscode/test-electron; the desktop MCP only as a complement; success, error and cancel flows each; screenshots and traces on failure; no real credentials anywhere.
VC6. EXTEND, DO NOT REBUILD; NO COLLISIONS: server additions in new files; surgical hooks after owners are done (Connect, multi-user retrofit); the storage declaration (PLAN-15) for anything new.
