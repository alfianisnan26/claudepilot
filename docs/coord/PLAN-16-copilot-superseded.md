## 1. Audit seed (K1 verifies it)
- Connect (docs/prd/targets-connect.md, in flight T1-T4): enrolled hosts and dockerized singles become workspaces (runtime kind `local` or `docker` over the tunnel); until then Docker workspaces on the DinD target are the testbed; the workspace image is images/workspace/Dockerfile (Claude Code is pinned by V1's work: an exact build arg; a Copilot CLI install must follow the same exact-pin discipline and not fight V1's file: coordinate through the coordinator).
- Secrets & env (apps/server/src/secrets, delivery, docs/prd/secrets-env-pool.md): secrets are sealed in the store and delivered to a workspace as files under /etc/claudepilot/secrets/files/NAME or as variables; "tool logins" (S2) are designed (a GitHub login with token-only files) but may be only partly built: find out; the portal never logs values; rotation and revocation exist.
- MCP catalogue (docs/prd/mcp-builtin-catalogue.md, mcp-providers.md): the GitHub template is token-only because GitHub's authorization server has no dynamic registration and its OAuth apps need a client secret; this POC's device flow is a different thing (a portal-side OAuth device flow with only a client ID: no client secret).
- Chat controller: apps/server/src/chat is the Claude Code stream-json engine; the Copilot CLI is a different program: for this POC it is a TERMINAL tool (the workspace terminal feature, apps/server/src/workspaces/terminals.ts and the web terminal), not a chat engine. A chat adapter is recorded as a risk and a next step, not built.
- Accounts: workspaces/claudeLogin.ts is the precedent for a guided sign-in in a pty; apps/server/src/accounts has the account pool (a Copilot token is NOT a Claude account: keep it out of the account pool).

## 2. Principles
K1. VERIFY FIRST WITH THE REAL CLI, WITHOUT CREDENTIALS: install the real Copilot CLI (pin an exact version; record the package name, version, install method and size) in a throwaway workspace container or scratch dir; read its docs and `--help`; observe, with BOGUS tokens and with no token, the exact error text and exit codes per auth input: which environment variables it reads and their precedence, the config and credential paths (is a token stored in a file, in a keychain, in a config dir?), the device-flow command, non-interactive use. From documentation and observation only (never a real login) determine: which token TYPES the Copilot API accepts (fine-grained PAT with the Copilot permission, classic PAT, OAuth device-flow token from the CLI's own client, a token from a custom OAuth app, a GitHub App user token), and whether a custom OAuth app's client ID can obtain a token the CLI accepts. Record every fact in docs/prd/copilot-poc.md with a mark: observed here (with the output), documented (source and date), or UNVERIFIED (what only a real Copilot seat can confirm). Never claim a pass you did not observe.
K2. MANUAL PATH: the token is a normal sealed secret (hidden file or variable, never an argument), delivered through the existing delivery pipeline; the Copilot CLI is installed into a workspace (an exact-pin install into the image as a layer or into the home volume on demand: choose with reasons, keep it out of V1's Claude Code pin file); "connected" comes from a real check run inside the workspace (the cheapest command that proves auth without spending model quota if one exists, otherwise a status the CLI can print; if nothing can prove it, show "unknown" and say why), cached with a time, never a flag.
K3. OAUTH DEVICE FLOW FROM THE PORTAL: only a client ID, from an environment variable (for example PORTAL_GITHUB_CLIENT_ID; absent = the OAuth path is unavailable and says so); request a device and user code from GitHub's device endpoint, show the user code and the verification link (a copy button and an open link), poll at the server's interval with slow_down, expiry, access_denied and success handled, store the resulting token in the Secrets store (sealed), show which scopes were requested and granted; the polling continues server-side so the person may close the dialog; rate limits, a timeout, cancel, audit; outbound calls only to the GitHub hosts through the outbound SSRF guard; NO client secret anywhere in the portal; a GitHub App for the web flow or issue/PR access is a documented NEXT STEP whose secret would live in the Secrets store.
K4. NO REAL CREDENTIALS IN TESTS: a stand-in GitHub device and token endpoint (extend the pattern of apps/server/src/mcp/builtin/testkit), a fake `copilot` CLI for the workspace-side check, tests that plant a canary token and prove it never reaches a log, a response, an audit row, a process argument list or a transcript.
K5. RISKS RECORDED HONESTLY in the PRD: a chat adapter for the Copilot CLI (what protocol it offers, if any; what an adapter would involve); LICENCE AND SEATS (a token belongs to one GitHub user with a Copilot seat; sharing one token across portal users may breach the terms; who pays; what the portal can and cannot verify); TOKEN SCOPES (least privilege, what a leaked token can do, expiry and rotation); data handling (what the CLI sends where).
K6. EXTEND, DO NOT REBUILD; NO COLLISIONS: Connect (T1-T4) and the version pin (V1) are in flight: add files, touch shared files surgically after re-reading, list every such edit; the authz seam rules apply to new routes; the storage declaration (where, size, retention, trust, behaviour on delete/detach/unreachable) goes in the PRD.
K7. UI: short (titles of 1-2 words, InfoTip), the QA bar, 390 and 1280 px, light and dark, screenshots looked at: a small "Copilot" card where a workspace's connections live (the Configuration sheet or the Secrets/tool-login area: choose by the code) with the two paths (Token | Sign in), the device code and link, a status chip from the real check, and Disconnect.
