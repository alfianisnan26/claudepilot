## 1. Audit seed (the agents verify it)
- Connect (docs/prd/targets-connect.md; T1 tunnel library landed, T2 agent, T3 runtimes, T4 installers in flight; T5 wizard UI not started): enrolled hosts and dockerized singles are targets; the agent dials OUT to the portal (reverse connect); enrollment uses a short-lived single-use token passed as a header or environment variable; the installer scripts are static and read a per-token plan. A codespace is a Linux devcontainer (usually non-root `vscode`/`codespace` user, Docker-in-Docker optional) in GitHub's cloud: it can run the Connect agent as a "single host" (host-native in the container) IF the portal's /connect/ endpoint is reachable from GitHub's cloud (a public portal URL: the deployed portal at the owner's domain is; a local dev portal is not). `gh codespace ssh` is the alternative: the PORTAL (or a helper) dials in through GitHub's SSH proxy with a token.
- Secrets & env (apps/server/src/secrets, delivery): sealed secrets, delivered as files or variables; Codespaces has its own secrets (user, repository and org secrets exposed to a codespace as environment variables, set by API): the enrollment token and the Claude login/credentials must reach the codespace through a path that never logs them (check what the Codespaces secrets API needs).
- MCP catalogue (docs/prd/mcp-builtin-catalogue.md, mcp-providers.md): the GitHub template is token-only (GitHub's authorization server has no dynamic registration; a GitHub OAuth App needs a client secret for web flows). The DEVICE FLOW needs only a client ID: it is how this POC authenticates the portal to GitHub (OAuth App or GitHub App with device flow enabled): verify.
- Claude Code version pin (PLAN-7, V1 in flight; docs/prd/claude-version-pinning.md): the devcontainer must install an EXACT Claude Code version and switch auto-update off the same way the workspace image does; reuse V1's registry and do not edit its files.

## 2. Principles
CS1. VERIFY THE API FIRST, WITHOUT CREDENTIALS: from the official docs (read with WebFetch) and unauthenticated public discovery only, determine the REST endpoints and exact request/response shapes for: listing repos and devcontainer configs, machine types (and their availability/prices if exposed), creating a codespace (repo, ref, machine, devcontainer_path, idle_timeout_minutes, retention_period_minutes, display_name, geo/location), getting its state (the full state list), start, stop, delete, export; and the AUTH each needs: fine-grained PAT permissions (Codespaces, Codespaces lifecycle admin, Codespaces metadata, repository permissions), the classic `codespace` scope, OAuth App vs GitHub App user tokens, org policy effects. Record every fact with a mark: documented (source and date), observed with the stand-in, or UNVERIFIED (needs a real account).
CS2. AUTH: manual token = a normal sealed secret; device flow = only a client ID (env var, e.g. PORTAL_GITHUB_CLIENT_ID; absent = unavailable and says so): request device and user code, show code + link, poll with the server's interval (slow_down, expiry, access_denied, success), store the token sealed in the Secrets store, show requested/granted scopes; the polling runs server-side; rate limits, timeout, cancel, audit; outbound only to GitHub hosts through the SSRF guard; NO client secret anywhere; a GitHub App for web flow or issue/PR access is a documented next step with its secret in the Secrets store. Tokens never in logs, argument lists, responses, transcripts; tokens are bound to the person who connected them (multi-user: "who may create a codespace with whose token" is an explicit rule: default = only the owner of the token, and a token is never usable by another user without an explicit share, via the authz seam).
CS3. LIFECYCLE: a provider module that maps the Codespaces REST API to the portal's runtime concepts: create (repo, ref, machine, devcontainer path), poll to Available, start, stop, delete, list; every state mapped (Provisioning/Queued/Starting -> creating, Available -> running, Shutdown/Archived -> stopped, Failed/Unavailable -> error, Deleted/gone -> removed); rate limits and backoff; cost/quota shown only if the API exposes it (else unavailable with the reason); idle timeout and retention shown and settable within limits; a keep-alive only if the docs and tests show it is needed and allowed (never a hack that burns quota silently).
CS4. THE WORKSPACE INSIDE: the devcontainer.json (or a Dev Container Feature) installs (a) the Connect agent as a single host (enrollment token delivered by a Codespaces secret or another documented path; the agent dials out to the portal's /connect/ endpoint; plain http only with the existing env flag) and (b) Claude Code at an exact pinned version with auto-update off, the same way V1 does it; postCreateCommand vs postStartCommand vs a feature: choose by testing; works for non-root images; idempotent on restart; "connected" derives from the REAL state (the agent's heartbeat and a real `claude --version` check), never a flag. COMPARE the transports with evidence: reverse connect (needs the portal reachable from GitHub; works through NAT; survives stop/start with the identity persisted in the codespace's volume) vs `gh codespace ssh` (the portal dials in through GitHub's proxy with the token; no inbound portal exposure; needs the gh CLI and a token on the portal side; what it can and cannot carry (terminals, exec, file put/read, ports)); recommend one primary with reasons.
CS5. PORTAL BEHAVIOUR: Unreachable when the codespace is stopped or the agent has not connected; a Start action (API start, then wait for the agent); "Detach from portal" (the portal forgets the target and drops its index; the codespace stays, and its enrollment is revoked) vs "Delete" (the codespace is deleted through the API after a confirm that names what is lost); idle timeout and keep-alive honesty; the target appears in the Connect wizard as a third kind ("Codespace") alongside cluster and single host (the wizard UI is T5's: add through its registration seam after it exists).
CS6. NO REAL CREDENTIALS, STAND-INS: a fake GitHub API (device flow endpoints + the Codespaces endpoints with a small state machine and the permission checks), and the REAL `devcontainer` CLI (@devcontainers/cli) running the SAME devcontainer.json in Docker-in-Docker on the scratch daemon, with a stand-in portal for the agent to connect to; tests plant a canary token and prove it never reaches a log, response, audit row, process argument list or transcript.
CS7. RISKS RECORDED HONESTLY: cost and quota (machine types, core-hours, storage, who pays: personal vs org billing, spending limits), token permissions (least privilege, what a leaked token can do, rotation), organization policy (allowed machine types, repository access, secrets policy, devcontainer restrictions), non-root user and image constraints, retention and automatic deletion (default idle timeout and retention periods; losing uncommitted work), multi-user (whose token creates, who may use a codespace, per-user billing), data handling (code and credentials in GitHub's cloud), availability (the portal must be reachable for reverse connect).
CS8. EXTEND, DO NOT REBUILD; NO COLLISIONS: Connect (T1-T4), V1 (version pin), P5 (authz), the MCP catalogue are done or in flight: add new files, touch shared files surgically after re-reading, list every such edit; storage declaration for anything new; the QA UI bar for any screen; clean environment for every program run.
