## 1. Starting hypotheses (the coordinator's; the architect challenges, improves and corrects them)

H1. REVERSE CONNECT: an agent installed on the target dials OUT to the portal (WebSocket over HTTPS), so the portal needs no inbound reachability (NAT, firewalls, Cloudflare tunnel and Caddy all work). This is the "control plane that opens traffic to the server": a small connector per cluster (per node for swarm), a runtime-in-a-box for a single host.
H2. TUNNEL: one authenticated, multiplexed connection per agent carrying named streams (`docker` = the local Docker socket or Windows named pipe, `kube` = the Kubernetes API through the agent's service account, `host` = exec, pty and files for a single native host). The portal side exposes each stream to the EXISTING runtime code as a local endpoint (a per-target loopback or unix-socket listener, or a custom transport), so `docker.ts` and `kubernetes.ts` work over a tunnel with minimal change and every existing feature (create, exec, shell, put/read delivery, usage, watch) works remotely. Verify this against how docker.ts and kubernetes.ts build their clients; pick the least invasive seam.
H3. ENROLLMENT: the wizard mints a short-lived, single-use enrollment token bound to the choices (kind, name, platform). The agent exchanges it for its own long-lived credential (a key pair it generated; the portal stores only the public key), can be rotated and revoked from the portal, and every connection is authenticated by signed challenge. Tokens appear in the pasted command, so: short TTL, single use, never logged, never in the audit text.
H4. THE SCRIPT: generated per wizard choice and served by the portal (`curl -fsSL https://<portal>/install/<id> | sh` for Linux/macOS, `irm https://<portal>/install/<id>.ps1 | iex` for Windows), viewable before running, idempotent, with checks (docker or kubectl present, versions, reachability of the portal), proxy support, checksums for what it downloads, and generated uninstall and upgrade commands. The agent arrives either as a container image the script builds from a context served by the portal (no registry needed) or pulls from a registry, or, for a native host, as a self-contained bundle with its own Node runtime under the user's home (no root where avoidable) installed as a systemd user unit, a launchd agent or a Windows scheduled task.
H5. KINDS (the matrix the wizard offers): cluster = docker socket (one Docker host or Docker Desktop), docker swarm (an agent per node as a global service; the portal places plain workspace containers on chosen nodes rather than swarm services, because workspaces are interactive and stateful), kubernetes (a Deployment with a namespaced ServiceAccount and a minimal Role, one manifest applied with kubectl). single = dockerized (the container IS the workspace: workspace image plus agent) or host-native (the agent runs the workspace on the host itself, with an explicit consent that there is no isolation; it generalises today's "This machine" target to remote machines).
H6. THE TARGETS PANEL becomes one registry: auto-scanned targets (docker socket, docker host socket, self/this machine, kubeconfig) stay, labelled "scanned"; enrolled ones appear beside them with status (connected, last seen, version, latency, nodes, capacity), actions (rename, rotate, upgrade, drain, remove) and the "Add" wizard entry. A workspace placement choice picks a target; a "single" target is a workspace by itself.
H7. LEAST PRIVILEGE: a docker.sock is root on that host. The docker stream goes through a filtering proxy in the agent with a default "workspace-safe" profile (only labelled `claudepilot-*` resources, no privileged, no host bind mounts outside the workspace's own, no host namespaces) and an explicit "full" opt-in; Kubernetes uses a namespaced Role, never cluster-admin.

image distribution to a remote Docker host (the workspace image is built locally today) and its versioning; where volumes live remotely (docker volumes, PVC storage class); placement, default target, quotas and capacity; web previews and the browser pool's ports through the tunnel; terminal latency and backpressure; large file transfers; agent and portal version compatibility and auto-upgrade policy; offline or proxied hosts; clock skew; token leakage through shell history; `curl | sh` trust (show the script, checksums, signed manifest); TLS rules (HTTPS required except loopback); revocation and what happens to running workspaces when a target disconnects (they keep running; the portal shows "unreachable", never deletes); reconnect storms and rate limits; audit trail; diagnostics (`pilot-agent doctor`); observability into Usage and Monitoring; Windows specifics (Docker Desktop named pipe, WSL2, native host); macOS specifics (Docker Desktop, launchd); what "swarm" really needs; multi-portal safety (the `claudepilot.portal` label rule); migrating today's static targets.
