### QA-001 [P1] [core] Open sockets survive sign-out, code rotation and session expiry
- Where: `apps/server/src/live.ts`, `apps/server/src/workspaces/shell.ts` (A2's file), `apps/server/src/chat/socket.ts` (A2's file). The session is checked once, at the upgrade.
- Steps: sign in twice (A, B); open `/api/live` (or `/api/chat/live`, or a shell socket) as B and subscribe; `POST /api/logout` as B, or `POST /api/admin/code` as A (signs B out). Watch B's socket.
- Expected: the socket closes (4401) when its session ends. Actual: it stays open and keeps receiving frames (verified: 2 `usage` frames after sign-out, 2 after the code rotation). For the shell socket this means a code rotation does not cut off an intruder's terminal in a workspace.
- Evidence: script `/tmp/qa-scripts/revoke.mjs` (frames received after revoke: 2 and 2, `closed=false`); same code path in all three socket files.
- Fix: a central guard (`apps/server/src/sockets.ts`, wired in `index.ts` before the other upgrade listeners) that tracks the raw socket per session token and destroys it on sign-out, rotation and expiry. Needs no change in A2's files.
- **fixed by A1**: `apps/server/src/sockets.ts` (new `SocketGuard`, attached first in `index.ts`) keeps each upgraded socket under its session token and destroys it on sign-out, on a new server code (`Portal.onRevoked`) and on expiry (15 s sweep). Verified live: after the fix a signed-out or rotated-out session's socket closes (1006) and receives 0 further frames. Tests: `apps/server/src/qa/sockets.test.ts` (4).

### QA-002 [P2] [core] Mutating requests with a JSON content type ignore the Origin check
- Where: `apps/server/src/app.ts` (`app.use('/api/*', csrf())`). Hono's `csrf()` only inspects form-like content types (`application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`, and no content type).
- Steps: `curl -b jar -H 'Origin: http://evil.example' -H 'Content-Type: application/json' -X PUT -d '{"enabled":true}' localhost:3101/api/admin/enabled` returns 200. The same with `Sec-Fetch-Site: cross-site` returns 200. With `text/plain` or no content type it is 403.
- Expected (PLAN rule 10, "Origin check on mutating requests"): a mutating request from another origin fails whatever its content type. Actual: only the browser's own CORS preflight and the `SameSite=Strict` cookie stand in the way. Not exploitable from a browser today (a JSON POST needs a preflight and the server sends no CORS headers), so this is defence in depth, but it is exactly the gap that a same-site sibling app (another port on the same host) or a future `Access-Control-Allow-Origin` would open.
- Fix: refuse any non-safe `/api` request whose `Origin` names another host than `Host` (host compare, not scheme, so a TLS-terminating proxy keeps working), regardless of content type.
- **fixed by A1**: `app.ts` refuses any non-GET `/api` request whose `Origin` host differs from `Host`, or that is marked `Sec-Fetch-Site: cross-site`, whatever the content type (host compare, so a TLS-terminating proxy that keeps Host still works). Verified live (evil Origin + JSON now 403, own origin 200). Tests: `apps/server/src/qa/auth.test.ts` (7; also the authorization matrix over every registered route, which is dynamic: new routes are covered automatically).

### QA-003 [P1] [core] The private-address (SSRF) guard for custom endpoints is bypassed by IPv6 spellings of private IPv4 addresses
- Where: `apps/server/src/accounts/check.ts` `isPrivateAddress`. `new URL('http://[::ffff:127.0.0.1]').hostname` is `[::ffff:7f00:1]`; the guard only strips an `::ffff:` prefix followed by dotted-quad text, so the hex form is judged public.
- Steps: with "Allow private network" OFF, create an endpoint with base URL `http://[::ffff:127.0.0.1]:4599` (or `http://[::ffff:169.254.169.254]`, `http://[::ffff:192.168.0.1]`, `http://[64:ff9b::7f00:1]`, `http://[::7f00:1]`) and add a key: the check calls it. Script `/tmp/qa-scripts/ssrf.mts` shows `ALLOWED` for all of them.
- Expected: blocked like `http://127.0.0.1`. Actual: the portal fetches loopback, link-local (cloud metadata) and LAN hosts on behalf of a signed-in admin. Mitigation: admin-only, response bodies are not echoed except provider error text (300 chars, via `redact`).
- Fix: parse IPv6 properly and judge the embedded IPv4 (mapped, compatible, NAT64, 6to4, Teredo), plus the other special-use ranges. Regression test in `apps/server/src/qa/ssrf.test.ts`.
- **fixed by A1**: `isPrivateAddress` now parses IPv6 and judges the embedded IPv4 (mapped, compatible, SIIT, NAT64, 6to4) and the special-use ranges; non-addresses are refused; `embeddedIPv4` exported (A3a: `mcp/spec.ts` compares `METADATA` by string, so `http://[::ffff:169.254.169.254]` still passes its metadata check even with private networks allowed; use `embeddedIPv4` there; **done by [A3a]**: `mcp/spec.ts` now does). Tests: `apps/server/src/qa/ssrf.test.ts` (6).

### QA-004 [P3] [core] No Content-Security-Policy; API responses are not marked `no-store`
- Where: `apps/server/src/app.ts` `secureHeaders({ strictTransportSecurity: false })` sends the Hono defaults only (no CSP). `GET /api/admin/state` (the server code in clear), `/api/admin/system`, session transcripts and the Secrets pages carry no `Cache-Control`.
- Expected: a CSP as a second wall behind React's escaping (this app has no `dangerouslySetInnerHTML` sinks on the paths I tried; see QA-0xx XSS sweep), and `Cache-Control: no-store` on `/api` JSON. Checked against the production build in Chromium: all pages, the session transcript and the terminal load with no CSP violation and no console error. A feature that needs another origin (an iframe, remote images) must extend `csp.ts`: `frame-src` and `img-src` are `'self'` (and `data:`/`blob:` for images).
