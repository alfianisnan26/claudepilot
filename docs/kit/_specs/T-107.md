# T-107 job-run: heavy agent work (tests, builds, browsers) runs as cluster Jobs, not in the pod

Owner asked (2026-10-13) how to make the whole setup faster and more effective. Decision: ONE workspace pod stays (no second pod: Claude sign-ins are per workspace, a new pod means re-login of all nine accounts). So the capacity has to come from OUTSIDE the pod. Today every test run, tsc, build and browser job of BOTH orchestrators and all their sub-agents queues on one flock (/tmp/heavy.lock) inside a pod that guarantees 1 CPU (limit 4) on a node at 95% requests, while k3s-master sits at about 30% CPU. The gate already runs as a Job (scripts/gate-job.sh) and went from 18-33 min to 5 min; do the same for everything heavy that an agent runs.

Build `scripts/job-run.sh` (and a Portal-side nothing: a script plus a Job template, in the pattern of gate-job.sh and dev-rig.sh, allowed in .claude/settings.json):
  scripts/job-run.sh [--repo claudepilot|konfersi] [--ref <branch or commit on the remote>] [--steps ...] -- <command>
1. The code: a pushed branch or commit (a sub-agent pushes its WIP branch first: `git push origin HEAD:wip/<name>`; ClaudePilot from GitHub as the gate does, Konfersi from Gitea with a Secret made for the Job's life and deleted on exit, the token never printed or logged, the log searched for it like gate-job.sh does).
2. The Job: prefers a node WITHOUT a workspace pod (the anti-affinity of gate-job.yaml), requests 1 CPU, limit 4, /tmp as a memory emptyDir (3 Gi), activeDeadlineSeconds, ttlSecondsAfterFinished, the workspace dev image (node, chromium, python, playwright deps) so nothing is downloaded; npm ci with a shared cache (an emptyDir seeded per Job or a read-only cache PVC; measure what is faster).
3. Output: the command's log streamed back, the exit code as the script's exit code, a short summary line; artifacts (screenshots, junit) copied back to a path the caller names (small, capped).
4. Caps and fairness: at most N Jobs at once cluster-wide for agents (a setting, start with 3) and at most 2 per chat; a Job over the cap waits in the script with a visible 'queued behind K'; each Job labelled with the session and role for the owner to see; a Job killed when its chat ends (reuse scripts/gate-job-stop.sh's approach).
5. Migrate the habits: docs/dev-sessions/README.md rule 4 ('heavy jobs through flock') becomes 'heavy jobs through scripts/job-run.sh; flock only for what must run in the pod'; the Konfersi roles' heavy.sh equivalent too (T-96 note); typecheck, vitest, playwright, lighthouse, builds, wrangler dry runs all go through it. Lighthouse and timing measurements run in a Job on a quiet node.
6. Tests: the script against the fake kubectl world (as wsResources.test.ts / deployPipeline.test.ts do): the Job manifest, the cap, the cleanup, the token never in a log; and one real run on the cluster: a sub-agent's vitest file, timed against the same file in the pod (write both times here).
Measure and report on this ticket: wall time of the full ClaudePilot suite and one Konfersi backend vitest run in a Job vs in the pod under today's load, and the pod's load average before and after a day of use.

Priority high, rank-03b (after T-105, before T-99): it removes the queue that slows both programs.
