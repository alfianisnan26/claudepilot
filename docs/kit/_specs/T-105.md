# T-105 Auto move must be proven: move at 10%, at once when exhausted, wait and resume when no quota

Owner, 2026-10-13: 'I never want to hit the limit again and not be able to move seamlessly.' Auto move must be PROVEN to work, end to end, for autonomous chats (Bypass, orchestrators, Konfersi). Requirements as the owner stated them:
R1. At 10% left (automove.thresholdPct, 'left' on the chat's own model window and the shared windows) the chat moves by itself to another Claude that has MORE than the threshold left.
R2. If the source is already past it (exhausted, 'You've hit your session limit'), it moves IMMEDIATELY, with no waiting period.
R3. If NO delegated Claude has more than the threshold left, auto move STOPS trying to move, says so once, and WAITS; it resumes by itself, with no person and no new turn, as soon as a destination is above the threshold again OR the source's own window resets, and then the chat continues its work.
R4. It works for a chat in Bypass (it keeps Bypass) and while sub-agents run.

What the coordinator found in the code (apps/server/src/autotransfer/engine.ts, decide.ts), 2026-10-13:
G1. R3 is NOT implemented. `case 'warn'` (no_destination) records one row and notifies once, then schedules NOTHING: the chat is evaluated again only at its next main-thread turn boundary. A chat blocked by the limit never ends another turn, so nothing re-evaluates it when quota returns. Today only a nudge from outside (supervisor) makes a new turn, which fails again until reset. Same for `session_cap`, `day_cap` and `paused` (only `paused` schedules a wake).
G2. Evaluation happens ONLY at a turn boundary (a `result` event of the main thread, then idle). A long turn (an orchestrator with sub-agents runs for hours) crosses 10% and never moves; it runs on until the limit stops it, and only then the boundary comes. R1 is not met for exactly the chats the owner cares about.
G3. After an automatic move that follows a limit error, nothing makes the chat continue: the interrupted turn is over. The handoff text exists, but no 'continue' is sent unless a supervisor nudges.
G4. Safeguards that can block a needed move: minPauseMin 30, maxPerSessionPerDay 2, maxPerDay 6, maxPerDestination 2. The coordinator already set (live settings) minPauseMin 5, maxPerSessionPerDay 8, maxPerDay 30, maxPerDestination 3; make these the defaults, and make the pause/caps NOT apply when the source is exhausted (R2) as long as the destination passes the ping-pong rule (the Claude it left in the last 4 hours stays excluded unless its window reset).
G5. Bypass chats were only 'suggest' until automove.allowBypass (on now); the Konfersi chat hit its limit at 11:57 on rossi with allowBypass off and was moved by hand.

Build, with tests on the fake clock (engine.test.ts and its testkit) AND a live check:
1. WAITING STATE: when the decision is warn/no_destination, session_cap, day_cap or paused and the source is at or under the threshold, keep a 'waiting for quota' state on the chat and re-evaluate on a timer (every 2 minutes, jittered, bounded; restart-safe: stored in the table the pending wakes use) until: a destination passes (then move), the source recovers above the threshold (then close the card/state), the chat ends, or the mode is turned off. The state shows on the chat (the auto move card says 'Waiting for quota: next Claude free at <time>', the soonest reset among the delegated Claudes) and in the trail (waiting, resumed).
2. EVALUATE ALSO WHILE WORKING: re-evaluate every chat whose source is at or under the threshold on the same timer and on every usage refresh, not only at a boundary. While a turn runs: do not move it mid-tool; send the chat ONE steer message (priority next, once per window period): 'Your Claude is at X% left: finish the current step, commit and push your work, then stop; the portal moves you and you continue.' and mark the chat 'moving at the end of this turn'. If the limit is hit anyway, the boundary comes and the move is immediate (R2). Never interrupt a running sub-agent for it; running agents stop with the old process, as a Move already says.
3. CONTINUE AFTER THE MOVE: after an automatic move, send the continuation to the chat on the new Claude when the last turn ended with a limit error or the steer message was sent: the transfer text plus 'continue where you stopped' (short; no secret; priority next). The Keep going policy (T-104) and this must not both nudge: one owner of 'continue after a move' (this).
4. Defaults as G4; the caps count only moves that were not forced by exhaustion.
5. Visible and testable: the trail kinds waiting, resumed, steered, continued; `GET /api/autotransfer/state` says per chat what it waits for; settings page text explains R1-R3 in one InfoTip. Tests: R1 at 10% (and not at 11%), R2 exhausted with a destination (no pause, no caps), R3 no destination then a destination appears (no turn boundary in between) and then the source resets, R4 Bypass and a running sub-agent, a portal restart while waiting, ping-pong exclusion, the steer message once per period. A live run on a scratch portal with the stand-in (tools/qa/automove.mjs) and one run against the real portal in a dry mode that only logs what it WOULD do for the live chats (a 'dry run' switch on the engine), result written on this ticket.
6. Report on this ticket the first time a real automatic move of an autonomous chat happens and verify the continuation by reading the chat.
