# T-133 New project onboarding: clone from an external git, start a new local repo, manage the project folder

Owner (2026-10-13): 'support onboarding to create a session either to GET a repo from an external git, or even CREATE a new repo locally to start fresh, and manage creating the project folder too, and so on.' (A new project will be developed from scratch with the same approach: see T-132.) What exists (coordinator, code and docs/prd/workspace-git.md section 4): the New session dialog starts a chat in an existing folder, optionally in a git worktree of a repository that already exists in the workspace (ChatWorktreeRequest: repo, branch, base); the Repos feature DISCOVERS repositories and reads their state; and its PRD lists as a NON-GOAL 'cloning or initialising: the portal never clones, pulls, merges, rebases, stashes, resets or cleans on its own'. So today a person must create the folder and the repository by hand in a terminal before a session can start, and an external repository can only be cloned by an agent already inside the workspace. This ticket makes starting a project a first-class, safe, guided action, and amends that non-goal: still never ON ITS OWN, but yes as an explicit, confirmed, audited action by a person (and by an agent only with a confirmation_required preview).

BUILD (phone first at 390 px, then 1280 px; the design standard; text diet; both themes). A 'New project' flow (also reachable from New session: 'Start from'):
1. SOURCE, four ways: (a) CLONE from an external git (https or ssh URL; shortcuts for GitHub, Gitea, GitLab, a self-hosted host; branch or tag; shallow option; sparse option for big repos): the URL goes through the SSRF guard and a host allow-list the owner edits (default: github.com, gitlab.com, the Gitea host); credentials only by NAME from a Secrets pool (a private repo needs a credential entry; the flow can create the pool entry from a one-time paste that is stored through the secrets API and never shown again, never in a log, an audit row or a transcript); (b) CREATE a new repository locally: name, default branch (main), .gitignore, README and license templates, an initial commit authored by the portal's agent identity with the Pilot trailers, optional second remote `pilot` (the local CI remote of T-94's pattern: create it and connect it so pipelines work at once); (c) FROM A TEMPLATE: the operating kit's project template (T-132) scaffolds the repository (CLAUDE.md, docs layout, .claude/settings.json baseline, .pilot pipelines, scripts); (d) EXISTING FOLDER in the workspace that is already a repository (the Repos list picks it).
2. WHERE: the workspace (a Kubernetes pod, a Docker box, This machine, a Connect target), the project folder under a convention (`~/work/<project>` and a sibling `<project>.worktrees/`, names checked: plain, unique, no path escape), disk and size checks BEFORE the clone (a size estimate from the host API where available, a cap setting, free-space check in the workspace), a name collision says so and offers the existing folder.
3. WHAT TO SET UP in the same flow: the persona and the kit's pools for the workspace (default: the `pilot-way` template), the Keep going policy (T-104) and whether the orchestrator chat is in Bypass (the owner's policy and acknowledgement rules apply: the flow never enables Bypass by itself), a ticket bucket (T-30) and the first tickets from the template, the budgets, and an optional first prompt that starts the orchestrator chat in the new folder.
4. EXECUTION through the same exec paths the chat host and CI use (kubernetesDelivery exec, Docker exec, Connect), as a bounded job with a live log: every command is fixed in code (git clone with a credential helper that reads the secret FILE, git init, git remote add, git worktree add), never a shell built from input; timeouts, a size cap on the transfer, no hooks run from a cloned repository (core.hooksPath unset or pointed at a safe empty dir during clone; submodules are listed and offered, not initialised automatically); a failed step leaves nothing half done (the folder is removed if the portal created it and nothing was written by anyone else); progress and the result are visible and the project appears in Repos with its identity.
5. MANAGE THE PROJECT FOLDER afterwards: rename, move, archive and delete a project, each with a safety summary ('this removes 3 worktrees and 2 unpushed commits on branch x: not pushed anywhere'), default KEEP (the worktree rules of chat-sessions already do this for sessions: reuse them); a project is a record that groups its folder(s), repositories (modules, T-134), chats, tickets (bucket) and pools.
6. FOR AGENTS: Portal MCP tools `project_create`, `repo_clone`, `repo_init` (confirmation_required with the preview: what will be cloned, where, size, credential NAME; the host allow-list and size cap enforced; secrets never pass through arguments: a call that contains something key-shaped is refused as everywhere), so an orchestrator can start a module or a sibling project.
7. SAFETY (hard): SSRF guard and allow-list; credential by name only; no secret in logs or transcripts; no executing of anything from a cloned repository at clone time; a repository's `.claude/settings.json` from outside is untrusted: the folder-trust scan runs before any chat starts there and a repo that loads hooks, MCP servers or env stays untrusted until a person trusts it (T-38 semantics: only permission rules are auto-trusted); the authz seam (`operate` on the workspace); audit rows; rate limits; a cap of projects per workspace.
8. TESTS: each source against a local bare repository (no network), the allow-list and SSRF refusals, a private repo with a credential name (fake helper), a failure at each step leaves nothing behind, the name and path rules, a repository with a hostile `.claude/settings.json` and hooks (must come up untrusted), the size cap, the exec paths on the fake Kubernetes and Docker kits, the MCP tools and their previews, the web flow at 390 and 1280 px with screenshots you LOOK at (harness), PRD workspace-git.md section 4 amended (the new rule written exactly) and chat-sessions/web-app updated: observed, not hoped; DECISIONS.md D-27.
Priority high, wave 2, rank-07a: after the autonomy and measuring block, before the multi-module ticket; the folder and repo creation (sources b and d) first because they need no network, then clone (a), then the template (c) once T-132 slice 5 exists.
