WHAT A TESTING AND DEVELOPMENT WORKBENCH NEEDS (build the missing parts, in this order of value):
A. AGENT CONTROL (MCP), complete and safe: the Playwright MCP inside the workspace stays the way an agent DRIVES pages; the PORTAL MCP gets the control plane for agents and for an external client (the owner's Claude): `browser_status` (state, tabs, viewers, who holds control, memory, last action), `browser_start`, `browser_stop`, `browser_restart`, `browser_reset` (confirmation_required, it signs the browser out of every site), `browser_set_device` (phone and desktop presets with touch, DPR, safe-area insets as CLAUDE.md asks for UI checks; custom sizes capped), `browser_tabs` (list, focus, close), `browser_screenshot` (an MCP IMAGE block, a region or the page, JPEG or PNG with a quality and a max size so one call is bounded; rate limited; refused in Private), `browser_record_start`/`browser_record_stop` (video, trace and HAR as artifacts, below), `browser_artifacts_list`/`browser_artifact_get`, `browser_console` and `browser_network` (the last N entries, filtered, redacted, capped: for debugging a page), `browser_throttle` (CPU 4x, network profiles like fast 3G, offline) so the phone profile of the harnesses is one call, `browser_policy_get` (blocked sites, allow-list, headers injected for named hosts), `browser_handoff` (exists; keep its rules). Same authz as every tool: scope, the workspace's agent access, the pool's tool rules; a call while a person holds control is refused with who and until when; every call audited with its actor label; results text is untrusted data (page text, console lines) labelled as such; no secret in any argument (key-shaped content is refused as everywhere).
B. TESTING AIDS: (1) ARTIFACTS: screenshots, video, Playwright traces, HAR, console logs captured during a run or a recording are saved in the workspace and referenced by id from the chat, a ticket (T-101 attachments), a CI run and a knowledge note (T-106), with caps and retention, never inlined beyond the cap, served authenticated; (2) NETWORK CONTROL: header injection for NAMED hosts only, values by secret NAME from a pool (Konfersi stg sits behind Cloudflare Access service-token headers: the browser must reach it without the agent ever seeing the token), request interception and mocking rules per run, and reaching the workspace's own dev servers (localhost ports) and cluster services as the egress policy allows; (3) VISUAL CHECKS: screenshot baselines per route and viewport with a pixel and structural diff and a review UI (approve a new baseline: a person or the QA role with evidence, never the author), reusing the harness shape of tools/qa; (4) PERFORMANCE AND ACCESSIBILITY: Lighthouse and the accessibility tree through chrome-devtools-mcp on demand, run in a quiet browser (a Job, T-107) with the numbers stored for the charts (T-121); (5) PARALLEL BROWSERS: up to the caps (2 per Kubernetes target, 4 per Docker target) named per run, each with its own profile, so a sweep of phone sizes does not serialise; (6) RECORD AND REPLAY of an agent's browser run as a timeline (actions, screenshots, console, network) a person scrubs after the fact.
C. USER UX (phone first at 390 px, then 1280; both themes; the design standard; text diet; all the rules of CLAUDE.md including no page drag: the live view is a pinned full-screen page with its own gestures inside it): the live view with ADAPTIVE quality (frame rate and JPEG quality follow the measured round trip and the viewer's bandwidth, a clear 'quality' indicator, a battery-saver mode), an ACTION OVERLAY showing what the agent just clicked, typed or navigated to (a highlight and a short label) with a synchronised ACTION TIMELINE under the view that scrubs the recording, URL bar and tabs, a STEP MODE (the agent waits for a tap before each action, for a sensitive flow, with the next action named), take-over with the lease UX (who, since when, an obvious 'hand back'), the text bar and a working phone keyboard, clipboard paste into the page (explicit, one way), downloads and 'send a file' panel, a read-only console and network panel (devtools-lite), device presets, a record button, and a snapshot share (an authenticated link to a screenshot or a recording). States: starting, asleep (wakes on the first call), degraded, crashed (self-heals, says so), reconnecting, over the viewer cap, private (screen hidden, no screenshots), unavailable with the reason; every control 44 px with a visible reason when disabled.
D. STREAMING DATA, designed and proved (the heart of this ticket): the live view and recordings move a lot of data; a person's stream passes through the portal (the VNC bridge over exec streams, the proxy view): (1) BUDGETS enforced in code and asserted in tests: per viewer at most N kbit/s and F frames/s by quality tier, per browser at most V viewers, per portal at most S concurrent streams, with BACKPRESSURE (a slow reader drops frames, never queues without bound, and is cut after a timeout; memory per stream bounded), (2) the portal's EVENT LOOP stays under 30 ms of lag with the maximum streams running while chats stream and a CI run is read (a lag probe in the load test), (3) RECORDING is done in the workspace and never relayed frame by frame through the portal; only the finished artifact is fetched, with a size cap and a transfer that does not hold the event loop, (4) screenshots to agents are bounded (size, quality, rate), (5) the Kubernetes pod's requests are small (T-97's fit rule: the pod requests 1 CPU / 2 GiB, node2 has about 0.6 CPU of requests free): the browser container asks for little and the encoder cost is measured so a stream does not starve the agents, (6) the cost of a stream is shown in the Browser status (bytes, frames, CPU) and feeds the usage view (T-122) and the scoring's efficiency term when a browser run is long.
E. SAFETY (hard, tested as attacks): CDP never leaves loopback (a test that scans the pod), no Service or published port, the bridge enforces view-only unless the viewer holds the lease, Private hides the screen from other viewers and stops screenshots, a HOSTILE PAGE suite (a huge DOM, a script that burns CPU, popups and window.open storms, a download bomb, fullscreen and pointer-lock grabs, clipboard reads, a file chooser, a page that tries to reach cluster services and the metadata address (egress policy), a cross-origin cookie grab, a page that prints a fake instruction to the agent: the gate labels page text as untrusted), credential redaction in every output, the extension policy, Chrome sandbox status shown, memory guard at 80 and 88 percent exercised under a memory bomb, the idle stop and the wake race, the lease expiring mid-action.
F. TEST AND EVIDENCE (the deliverable, written on this ticket): a harness `tools/qa/browser-e2e.mjs` and `tools/qa/browser-stream.mjs` on a scratch portal with a real browser container (Docker here, the Kubernetes rig `dev-rig-browser`), covering: every MCP tool (contract tests with the schemas), the gate's rules (wake on first call, refuse under control, redaction), take-over and hand back, reconnect after a network drop, a viewer joining and leaving, the caps, crash and self-heal, idle stop and wake, recording to an artifact and its retrieval, step mode, device presets, throttling, visual diff approve flow, header injection by secret name (a fake host that echoes headers; the token must not appear anywhere the agent can read); and the STREAM numbers: input-to-pixel latency p50/p95 on 390 px phone and 1280 px desktop clients, frames per second and bytes per second at each tier, the portal's CPU, memory and event-loop lag with 1 and the maximum streams, the browser container's CPU and memory, frames dropped under a throttled client, memory flat over a 30-minute run, all against a budgets file checked in the gate (a regression fails it). The first full report goes on this ticket.
