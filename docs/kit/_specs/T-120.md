# T-120 ClaudePilot design standard: write down the UI standard the development follows (docs/design)

Owner (2026-10-13): ClaudePilot needs a written DESIGN STANDARD of the one its own development already follows. SCOPE: ClaudePilot only. Konfersi is out of scope: it has its own fully established design standard in Outline (nothing to write or copy for it, and no Konfersi agent is touched by this ticket).

What exists today and is NOT one document (found by the coordinator): the UI rules in CLAUDE.md (44 px touch targets, no horizontal scroll, text that breaks anywhere, lists that hold still, phone width 390 px first then 1280 px, light and dark, keyboard and touch; text diet: titles of one or two words, explanations in an InfoTip, icon-only on phones; numbers shown must have a source, 'unavailable' is a state; phone screens do not drag), docs/coord/QA-STANDARDS.md (A1-A9), docs/prd/web-app-pwa.md section 10.5 (phone chrome and the real-device checklist), the components in apps/web/src/components (Card, InfoTip, PageHeader, KeyBar, SettingRow, SecretField, AppShell, charts.tsx...), the helpers in apps/web/src/lib (viewport.ts, scrollGuard.ts, sheetDrag.ts), the glass header and tab bar, the status chips (Idle, Working, Needs you, Bypass, Ended...), and the base design system `@isnanme/ui` (pay's design system, a private package that apps/web builds on). Nobody can see in one place what a new screen must look like, and the recent UI tickets (T-100 clipped cards, T-102 the popover over the composer and the badge over a button, the header blur) are exactly the drift a standard prevents.

Write `docs/design/DESIGN-STANDARD.md` (and split into a few files under docs/design/ if it grows past about 500 lines, with one index), derived from the CODE and the owner's decisions, not invented: every rule cites the file or the PRD it comes from, and says 'observed' (seen in the running app at 390 and 1280 px, light and dark) or 'decided' (the owner's rule). Contents:
1. PRINCIPLES in a page: phone first, calm and dense, text diet, honest numbers, nothing moves under the finger, no drag, autonomy visible (what needs a person is always one tap away), and the owner's wording where it exists.
2. TOKENS: colour (surfaces, text, borders, the status palette with its meaning, accents, the Bypass tint, danger), type scale and weights, spacing scale, radii, elevation and the GLASS recipe (blur, tint, border, the fade under floating bars, safe-area insets), motion (durations, reduced motion), icon set and sizes. Generate the token table FROM the CSS/Tailwind source by a script (scripts/design-tokens.mjs) and check it in the gate so the doc cannot drift from the code.
3. LAYOUT AND NAVIGATION: the app shell, the floating header and tab bar (what goes where, how many items, the count badges and where they sit so they never overlap a button), pages vs sheets vs dialogs vs popovers (when each, their sizes, how they sit above the keyboard and the composer, close on outside tap and scroll), full-screen pinned pages, safe areas, landscape, the 1280 px desktop layout.
4. COMPONENT CATALOGUE: for each shared component: when to use it, when not, props that matter, the states it must show (default, loading, empty, error, unavailable, disabled WITH a visible reason), a screenshot from the harness, the checks that cover it. Include the lists (rows, groups, chips, swipe actions, pinned), forms and setting rows, secrets, charts and the status chips; mark what comes from @isnanme/ui and what is the app's own.
5. PATTERNS: lists that hold still (keys, reserved space, no shift), skeletons then data, empty, error with Retry, 'unavailable', long content (clamp, wrap anywhere, tooltips), destructive actions (confirm text names what is lost), toasts, optimistic updates, live updates without jumps, numbers with a source, text diet with an InfoTip example, copy tone (short, plain, no blame; the owner's language rules).
6. INTERACTION AND ACCESSIBILITY: 44 px targets, gestures that exist (swipe to pin) and the no-drag rules (lib/viewport.ts, scrollGuard.ts, sheetDrag.ts and the harnesses that check them), keyboard paths, focus rings, labels on every icon-only control, contrast AA in both themes, colour never the only signal (pattern or letter), reduced motion, screen-reader order.
7. ANTI-PATTERNS WITH EVIDENCE: the mistakes already made and fixed or open, each with its cause and the check that catches it (a row painting past its rounded container, a popover over the composer, a badge over a button, a disabled button whose reason is only in a tooltip, a hard edge under a blurred header, a chip order by habit instead of by attention).
8. CHECKS AND HOW A UI CHANGE IS REVIEWED: the tools/qa harnesses and what each proves (scroll-lock, mobile-drag, session-chrome, session-states, home, automove, session-swipe, tool-rows...), the QA-STANDARDS A1-A9 mapped to rules above, a short REVIEW CHECKLIST for every UI pull request (phone width, both themes, 44 px, no overflow, no shift, states, reasons, text diet, tokens only, screenshots looked at), and the standards-check hook (T-111): a UI change that uses a colour, a radius or a size outside the tokens, or a control under 44 px on touch, fails the harness, not a person's eye.
9. LIVING GALLERY: the dev-only UI lab of T-14 renders every component in every state with the extreme-data fixtures at both widths, and the harness takes the screenshots that the document embeds (regenerated by a script, so they never go stale). If T-14 is not built yet, build only the gallery part this ticket needs and say so on T-14.
10. DELIVERY TO AGENTS: a short Skillset skill `design-standard` (the rules in one page plus the pointer to the file) and a Context line, assigned by default to ClaudePilot's own workspaces only (through the mechanism of T-115; until it exists, the CLAUDE.md pointer), so every agent that touches apps/web follows it. Konfersi's workspaces do not get it.
11. WHERE IT LIVES: docs/design/ in the repo (the source), indexed from CLAUDE.md and docs/README; versioned; changes to it are a pull request with the harness green; the owner owns the rules, the agents may propose changes by ticket (charter walls: the standards check's thresholds are human-owned).
Done when: the document exists with every rule sourced, the token script runs in the gate, the screenshots are generated, one real UI change (T-100 or T-102) is reviewed against the checklist and the review is written on that ticket, and the owner has read the principles page. Not a rewrite of the UI: where the code and the rules differ, list the difference as a ticket, do not fix everything here.
Priority normal, wave 2, rank-08c (after T-106). It is documentation and one small script, not a feature: do it in small slices between the larger ones, principles and tokens first.
