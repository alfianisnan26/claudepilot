# T-132 Operating kit: the way of working as personas, skills, contexts, MCP sets and a project template

Owner (2026-10-13): 'I want this style of work put into personas, skills, contexts and MCP sets for other needs. P.S. there will be a NEW project, developed from scratch, whose approach will be at least the same as ClaudePilot and Konfersi.' Today the way of working lives in files that only a ClaudePilot chat reads (CLAUDE.md, docs/dev-sessions/README.md, CHARTER.md, DECISIONS.md, the briefs, the supervisor script, scripts/gate*.sh, .pilot/*.yml) and in Konfersi's docs/agentic. A new project would start with none of it. Turn it into REUSABLE PIECES of pilot itself, controlled from the portal, versioned, and applied by a template. Konfersi keeps its OWN program overlay and design standard (Outline): the kit is the generic base it can sit on, not a replacement for what is established there. ClaudePilot's own workspace becomes the first user of the kit (dogfood), keeping its project-specific parts as overlay.

THE KIT (each item is a pool entry or a template field; sources in this repo are the starting text, cleaned of ClaudePilot-specific names):
1. PERSONAS (Persona pool): `orchestrator` (plans in ranked tickets, WIP limit three, dispatches sub-agents in worktrees, integrates fast, releases safe, keeps the status file, never idles, escalates only what is required), `implementer` (a slice with tests, the trailers, the estimate), `qa-verifier` (independent: verifies the author's work with evidence, never the author; the qp/b9 pattern), `reviewer` (peer review rubric of T-114), `scribe` (PRD, docs, decision records), `release-coordinator` (gate, deploy, approval path, watching), `watchdog-analyst` (incident post-mortems). Each persona: role, scope, the charter's duties in its voice, what it must never do, its done criteria, the model tier it prefers (sonnet for sweeps, opus for implementation, fable for diagnosis nobody else cracked).
2. SKILLS (Skillset pool): `charter` (zero tolerance, duties, walls), `decisions` (read the registry before planning; record a decision on the record; conflict handling), `ticket-flow` (claim only when work starts, WIP three, structured estimate, rank tags, closing summary with evidence, unclaim), `git-flow` (worktree per slice, branch names `ticket/T-n-slug`, commit trailers Ticket/Pilot-Session/Pilot-Agent, small commits, push WIP early, never force push), `ci-cd` (gate-quick vs full gate, job-run for heavy work, the deploy pipeline and its approval path, reading a failed step log), `incident` (the report format of T-112/T-124 and the post-mortem with the check that would have caught it), `escalation` (required vs avoidable, the default-and-write rule, the one checklist), `safety` (secrets only through pools, never print a credential or the environment, deny rules are not worked around), `knowledge` (T-106), `efficiency` and `peer-review` (T-114), `design-standard` as a SLOT each project fills with its own (ClaudePilot's is docs/design, T-120; Konfersi's is in Outline).
3. CONTEXTS (Context pool): `charter-essentials` (always delivered, the zero-tolerance list in six lines and the pointer), `work-rhythm` (the status-file format: DONE, IN FLIGHT, DECISIONS, NEEDS A HUMAN, NEXT; commit and push cadence; the monitor loop), `project-standards` (a template the project fills: language and stack, test commands, UI quality bar, definition of done) and `program-overlay` (empty by default; Konfersi's RULES live here).
4. MCP SETS (MCP set pool): `pilot` (the Portal MCP: always, with T-115's instructions, resources and prompts), `git-host` (gitea-mcp or the GitHub MCP, credentials by name from a Secrets pool, never in the set), `docs` (the project's Outline or equivalent), `issues` (optional), `browser` (the Playwright MCP once the Browser pool exists on Kubernetes, T-97). Each with its review state and its secrets by `{secret-file:NAME}`.
5. PROJECT TEMPLATE (the workspace-templates PRD: image tag, persona, sets, repos, settings, limits): a template `pilot-way` that carries the above plus: the baseline `.claude/settings.json` (deny rules: force push, env printing, secrets, production tools, kubectl outside the doors; allow rules for the project's own scripts), the scaffolding of a NEW repository (CLAUDE.md from the template with the project's name and stack, docs/ layout: PRD folder, decisions, dev-sessions (README, CHARTER.md, DECISIONS.md, status), the `.pilot/` pipelines (gate, deploy with an approval environment, verify, rollback), scripts (gate.sh, gate-quick.sh, job-run.sh, dev-rig.sh pattern), the commit hook of T-27), the settings and limits (Bypass allowed for the orchestrator chat, session caps, the Keep going policy of T-104 with its lease, the watchdog enrolment of T-108, the auto-approve rule OFF by default, budgets and spike rules of T-129, the scoring enrolment of T-114), and the first tickets (a 'plan the PRD' ticket, a 'set up CI' ticket, a 'definition of done' ticket) with ranks.
6. VERSIONING AND DRIFT: the kit has a version; a workspace records which version it runs; the owner reviews an update (a diff of each pool revision) and applies it to chosen workspaces; the pool framework's revisions and rollouts already exist (foundation-pools PRD): reuse them, do not invent a second mechanism. The retro (T-111) proposes kit changes as pool revisions that need the owner's review where they touch safety (the charter's walls), and the adopted playbooks (T-114) land as skill lines.
7. PROOF: bootstrap a THROWAWAY project from scratch through the kit in a scratch workspace with the onboarding of T-133: the orchestrator chat starts with the persona, skills, contexts and MCP set, writes a small PRD, opens ranked tickets with estimates, builds a first slice in a worktree through the gate, deploys to a dry stg, writes its status file, records a decision, files an honest incident line, is moved to another Claude and continues: all with Keep going and no human message after the first prompt. Measure: minutes from 'create project' to the first green gate, tokens spent, human touches (the target is zero after the first prompt), what the agent still asked. Write the report on this ticket and fix the kit from it.
8. SAFETY AND AUTHZ: kit pools are admin-owned and read-only to agents (agent text never edits a persona or skill: proposals are tickets); the charter's walls hold; no secret in any pool entry text; applying a kit needs `operate` on the workspace and on every pool it names (the seam), a denial is the same 404; audit rows for apply, update, detach.
9. TESTS: the template creates the workspace with every pool assigned and the scaffolding in place (fake runtime), a version update shows its diff and applies it, a persona/skill can not be edited by an agent token, the project bootstrap test above as a rig, the pools' review states; PRD: persona-pool, skillset-pool, context-pool, mcpset-pool and workspace-templates get the kit section; DECISIONS.md D-26.
Priority high, wave 2, rank-04e: right after the MCP elevation (T-115, which delivers the charter and the decisions to agents) because the kit uses it; start with the pool CONTENT (items 1-4: text, no code) which can be done in small slices now, then the template and the scaffolding (5), then versioning (6) and the proof (7).
