# T-95 Deploy pipeline: fewer false failures

The deploy pipeline fails or is cancelled too often for reasons that are not the code. Of runs 1-9 on 2026-10-13: 2 passed, 5 were cancelled by hand (a newer push made them stale), 2 failed:

- Run 4 (release): `.pilot/scripts/release.sh` makes the release commit (manifest bump, 87ffc46 "portal 2026.10.13-3") on top of the run's sha and pushes it atomically to main AND integration, fast-forward only. integration had moved on during the 20-minute wait for the approval, so the push was refused (non-ff) and nothing deployed. Any push to integration while a run is open breaks it.
- Run 5 (gate): the full suite failed on one flaky test (hub.test "the control stream"), after 33 minutes (server-suite 1971 s on a loaded pod). Fixed since (3674941), but a flaky test still costs a whole run.

Fix, in this order:
1. release.sh must survive a moved integration. Push the release commit to main only (it fast-forwards main, because main is an ancestor of the run's sha), then bring integration up to date as a separate step: merge main into the current integration head (no force; if it conflicts, stop with a clear message). The atomic two-branch push goes away. Same for rollback.sh. Tests with a fake remote that moves between the gate and the release (deployPipeline.test.ts has the fakes).
2. The run says why it was cancelled and by whom (a stale-run cancel when a newer run starts for the same pipeline is fine; today the cancelled rows show only "cancelled").
3. The gate should take much less than 33 minutes: it already runs as a cluster Job (T-37); check its CPU request and the test concurrency there, so the suite is not slowed by the load of the pod. Report the numbers.
4. A gate failure on one test that passes when rerun alone is reported as "flaky, passed on rerun" with the test name in the run summary, and a ticket is made for it (tag flaky) instead of failing the deploy. scripts/gate.sh already reruns failing files alone: make sure the pipeline's gate does too and does not count a rerun-pass as a failure.
Until 1 is done: do not push integration while a deploy run is waiting for the approval (look with ci_run_list before every push).
