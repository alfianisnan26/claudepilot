# T-110 Auto-approve rule for an environment (the portal approves, never an agent)

Owner decision (2026-10-13) on T-108 item 3: YES. ClaudePilot's own deploys are approved by the PORTAL by rule, never by an agent (an agent still has no approve tool). The owner's reason: the system must be 100% autonomous, self-healing, self-learning and self-improving, and a deploy that waits for one person breaks that.

Build (PRD amendment first: docs/prd/local-git-ci.md FR41 says 'a person only': amend it to 'a person, or the environment's rule that a person turned on'):
1. An environment option `autoApprove` (off by default, set only by a person with `manage` on the remote, audited, shown on the run page and the environment list) with a rule of ALL of: the full gate is green on this exact commit (the gate job's verdict, not a flag); the build for this commit succeeded; `verify` and `rollback` jobs exist in the pipeline and the rollback's previous tag is known; the diff since the last released commit has no change under apps/server/src/authz, secrets, the Bypass code, .claude/settings.json deny rules, migrations of a released number, or a file the environment lists as 'needs a person' (a list the owner edits, defaults to those); at most N auto approvals per day (default 6) and one at a time; inside an allowed window (default always); the previous auto-approved deploy of this environment is not currently failing or rolled back.
2. What it does: approves the held job as the actor `rule:<environment>` with the reasons in the audit row and on the run page ('auto-approved: gate green at <sha>, 4 conditions met'); when a condition fails it does NOT approve, writes which one, notifies the owner once ('Needs you') and the run waits as today.
3. Safety valves: a big 'Pause auto-approve' on Home and the environment (instant, no deploy in flight is stopped, the next waits); automatic pause after one rollback or a failed verify until a person resumes it; the Home 'Autonomy' widget shows last auto approvals; every auto-approved deploy is listed on a ticket-like feed for the owner to read later, never to answer.
4. Trial: the coordinator (delegate) keeps approving by hand for 5 more green deploys while this is built; the owner turns it on after reading the first dry run (a mode `dry`: it says what it WOULD approve and approves nothing).
5. Tests: each condition refused with its own reason, the daily cap, the rollback pause, the pause switch, the audit row, the authz (only `manage` turns it on; an agent token cannot), a full pipeline run through the CI service with a fake runner, and a PRD line with what was observed.
