# T-134 Multi-module projects: several repositories with a worktree each per unit of work, and a git view for commits and branches

Owner (2026-10-13): 'make sure our sessions support MULTI-MODULE git WORKTREES, and a git UI/UX for COMMITS and BRANCHING: that should already be a request in ClaudePilot, right?' Answer from the code and the tickets (coordinator): PARTLY. (1) A session runs in ONE worktree of ONE repository (the session's `worktree` and `cwd`; ChatWorktreeRequest takes a single `repo`); there is no notion of a project made of several repositories. (2) The Repos feature (apps/server/src/repos, docs/prd/workspace-git.md) DISCOVERS 'a pool of repos like konfersi-universe' (17 clones in sibling folders) and reads their state, read only. (3) The git view of commits and branches is requested as T-26 (read only: branches with ahead/behind and merged state, commits per branch, which worktree and which session, a stale flag; on-demand scans of Kubernetes workspaces) and the commit trail as T-27 (Pilot trailers): both OPEN and NOT STARTED (T-26's 'in progress' was a false claim of the mass claim, see T-127). (4) Konfersi works around the gap by hand: its roles keep one clone per repo and topic under ~/work/agentic-worktrees with scripts, and its cross-repo tickets (a backend change and a console change for one feature) have no shared branch, status or CI view in the portal. This ticket makes multi-module work first-class and finishes the git view, together with T-26 and T-27 (do them as one design; read them first).

MODEL: a PROJECT (of T-133) has MODULES: each module is a repository (local path, upstream remote, default branch, its CI remote if any, its role: backend, console, docs...). A UNIT OF WORK (a ticket, a slice) gets a WORKSPACE OF WORKTREES: one linked worktree per module it touches, all on branches named by the same convention (`ticket/T-n-slug`) under `<project>.worktrees/<unit>/<module>`, created and removed together; a session may start 'in a unit' and its cwd is the unit folder holding the module worktrees (or the one module the ticket names), with the environment variable PILOT_MODULES listing them so tools and agents know the layout; sub-agents get their own unit folders the same way (replacing the hand-made agentic-worktrees pattern and its scripts).
BUILD, in order (each merged on its own):
1. PROJECT AND MODULE RECORDS: a project record groups modules (repositories the Repos feature already identifies by `r_` ids), with roles and conventions (branch pattern, default base, commit trailers, protected branches); discovery proposes the modules of a pool of repos ('this folder holds 17 repositories: make them a project?') and a person confirms; no hidden writes. API and Portal MCP read tools (`project_get`, `module_list`).
2. UNITS AND WORKTREES: `unit_create` (project, name, ticket, modules, base per module): creates the branch and worktree per module through the exec paths with fixed commands (never a shell from input), refuses a dirty base or a branch name collision, records which session and ticket own the unit, and `unit_remove` with the safety summary (unpushed commits, uncommitted changes: default KEEP; force needs the person); a session or ticket can be started 'in a unit' (the New session dialog and Start session on a ticket gain it); the existing single-repo worktree path stays and is the one-module special case; the chat-sessions worktree rules (safety on delete, archive keeps by default) are reused, not duplicated; crash and restart safe (the unit's state is on disk and in the record; a half-created unit is repaired or removed).
3. THE GIT VIEW (T-26's UI, multi-module aware; Repos > project; phone first at 390 px, 1280 px; both themes; the chart kit of T-121 for the graph): per project a MODULE STRIP (each module: branch, ahead/behind, dirty, last commit, CI state of its head, the unit and session on it); per module the BRANCH LIST (local and remote, merged or not, stale flag, which worktree has it checked out, which session, sub-agent and ticket), the COMMIT GRAPH of the last N commits as a lanes diagram (merges and branches visible, one lane per branch, commit dots coloured by author kind: person, agent, role; trailers parsed into chips: ticket, session, agent), a COMMIT SHEET (message, trailers, files changed with line counts, the diff read only with syntax colouring, the CI runs on that commit, the ticket and the chat that made it), and a UNIT VIEW that shows ONE ticket across modules (all its branches, commits and CI runs on one timeline: the shared timeline of T-119 with the commits as markers). All of it READ ONLY, as the PRD decides: no commit, push, rebase, merge, reset or stash from the UI. SAFE ACTIONS the portal may offer through the same fixed-command path, each confirmed and audited: create a unit or a branch+worktree for a ticket, remove a merged branch or an empty worktree, fetch a remote (never pull), and 'ask an agent' buttons that Bump a chat with the intent (rebase this unit onto main, open the pull request, resolve the conflict) so the work stays in a chat with its trail, never a hidden UI git write.
4. SCANNING AND PERFORMANCE: Kubernetes workspaces are scanned ON DEMAND (Scan button, when the view opens and the last scan is older than a few minutes, at a session start) through the kubernetesDelivery exec path with the repo-find and repo-state host scripts, bounded in time, repositories and output, rate limited per workspace, results stored and shown with their age ('scanned 3 min ago'); the 'never exec into pods on a timer' principle stays (PRD amended: on demand yes, on a timer no); the graph and branch APIs are paged with a cursor and capped (commits per page, branches per repo), p95 under 80 ms from the stored scan, response under 100 KB gzipped, EXPLAIN asserted, no event-loop stall (git is run in the workspace, never in the portal process, never synchronously), a seeded fixture of 20 modules and 5,000 commits; the graph is drawn on canvas or one SVG path per lane with row windowing: 60 fps on the 4x-throttled phone profile; harness `tools/qa/git.mjs`, budgets in the gate.
5. CI ACROSS MODULES: each module may have its own CI remote (the pattern of T-94); a unit's runs are listed together; a project-level pipeline (a `.pilot` file in a designated module) can check out several modules at the unit's branches ('build the console against this backend branch'); the Konfersi `stg-deploy` pipeline's `repo` input and its mirror job become the first user of a module's metadata (remote URL, mirror).
6. TRAILERS AND TRACE (T-27, done with this): the prepare-commit-msg hook delivered into workspaces appends the trailers (Co-Authored-By model, Pilot-Session, Pilot-Workspace, Pilot-Claude name, Pilot-Model, Pilot-Provider, Pilot-Agent, Pilot-Actor, plus Pilot-Unit and Pilot-Module here); the git view and the scoring (T-111/T-114: the unit that delivered a change, rework detection) read them; a commit without trailers is flagged by the standards check.
7. SAFETY: all git commands fixed in code with arguments validated (refs, paths, remote names), no hooks run from repositories at scan time, `safe.directory` handled, never follow symlinks out of the project, a repository's own config can't redirect the portal's commands, output redacted for credentials in remote URLs, authz through the seam (`view` shows the tree and status, never contents beyond the diff of a commit the person may see: PRD MO9), rate limits, audit rows for every action.
8. TESTS: unit create/remove with a dirty base, a collision, a crash in the middle; three modules and one ticket through worktrees; the graph parser with merges, octopus merges, orphan branches, shallow clones, empty repos, huge messages, hostile branch names (newlines, leading dashes, unicode); trailers parsing; scan bounds and rate limit on the fake Kubernetes kit; the phone view at 390 px; no overflow, lists that hold still; screenshots you LOOK at; PRD workspace-git.md and chat-sessions.md updated (observed); DECISIONS.md D-28. First write the AUDIT of what Konfersi's agentic-worktrees pattern needs (a list on this ticket, from its scripts and docs) so the model fits a real multi-repo program, not an imagined one.
