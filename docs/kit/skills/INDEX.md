# Operating kit: skills

The skills of the operating kit (Skillset pool). Each folder holds a `SKILL.md` (text only, at most 16 KB) and, for some, `references/` with templates and real examples. Roles are the kit's personas: orchestrator, implementer, qa-verifier, reviewer, scribe, release-coordinator, incident-analyst, explorer, ux-checker, perf-tester. "All" means every role and every sub-agent.

The skillset `pilot-way` holds all of them (prefix `pilot`); a workspace gets it by assignment (a separate, owner-confirmed step). Most useful everywhere: `charter`, `knowledge`, `efficiency`, `peer-review`. The project template says which roles use the rest.

Precedence when texts disagree: the charter, then standing decisions, then program rules, then the role's brief, then the ticket.

| Skill | Used when | Roles | Depends on (skills; planned portal features marked "when available") |
| --- | --- | --- | --- |
| `charter` | start of every session and unit; anything that feels off: a doubtful premise, a contradiction, a red check, a shortcut, bad news | all | `incident`, `decisions`, `escalation`, `qa-verification`; the charter resource and `session_context` (when available) |
| `decisions` | before planning; before any consequential choice; on any contradiction with an earlier decision | all; orchestrator records owner decisions | `escalation`; the decisions registry: `decision_search`, `decision_get`, `decision_record`, `session_context` (when available; until then the project's decisions file) |
| `ticket-flow` | picking, claiming, estimating, blocking, unclaiming, handing in, closing or writing a ticket | all | `decisions`, `qa-verification`; the structured estimate field, the claim gate on estimates, the ticket timeline, `scoreboard_me` priors (when available) |
| `escalation` | about to ask a person anything; a step in a required class; feeling stuck waiting | all; orchestrator keeps the checklist | `decisions`, `ticket-flow`; Keep going answering questions with "decide yourself" (when available) |
| `incident` | the moment an incident is caused or found; writing a post-mortem | all; incident-analyst writes post-mortems | `charter`, `knowledge`, `qa-verification`; incident accounting and the claim audit, the watchdog, knowledge attachments (when available) |
| `orchestration` | running a program as the orchestrator chat; after every restart | orchestrator | `ticket-flow`, `git-flow`, `ci-cd`, `qa-verification`, `escalation`, `efficiency`; Keep going and the watchdog, the portal's WIP limit, the scoreboard for routing (when available) |
| `qa-verification` | verifying another agent's delivered unit or any "done" claim | qa-verifier; release-coordinator for deploys; any role sampling | `ticket-flow`, `incident`, `browser-testing`, `ci-cd`, `design-standard`; the claim audit and the parent-commit regression check (when available) |
| `peer-review` | assigned to assess another unit; writing your own reflection; reading reviews of your work | reviewer; all for the self-reflection | `charter`, `efficiency`; `peer_review_next`, `peer_review_submit`, `peer_review_get`, the scoreboard (when available; until then ticket comments) |
| `efficiency` | before, during and after every unit | all | `ticket-flow`, `orchestration`, `peer-review`, `knowledge`; `playbook_search`, `scoreboard_me`, `my_efficiency`, in-flight spike steering (when available); `usage_summary`, `usage_attribution`, `usage_spikes` exist today |
| `portal-mcp` | any Portal MCP call; a tool answering `confirmation_required`, `RATE_LIMITED`, `SCOPE_REQUIRED`, `FORBIDDEN`, `UI_ONLY`, `CONFLICT` or `SECRET_IN_ARGUMENT` | all; release-coordinator for CI runs | `ticket-flow`, `knowledge`, `ci-cd`, `git-flow`, `safety`; project, module, onboarding, attachment and browser tools, settings proposals (when available) |
| `git-flow` | starting, committing, pushing, merging or cleaning up a unit; a conflict; a dirty base; several repositories | implementer, orchestrator, release-coordinator | `ticket-flow`, `ci-cd`, `safety`; the trailer hook, `unit_create` and `unit_remove` (when available) |
| `ci-cd` | before an integration push or a release; anything heavy; a red step or gate; a flaky test; a deploy waiting for approval | orchestrator, release-coordinator, implementer, qa-verifier, incident-analyst, perf-tester | `git-flow`, `safety`, `portal-mcp`, `escalation`, `incident` |
| `safety` | credentials, the environment, deny rules, the cluster, outbound calls, text from outside; a secret in sight | all | `incident`, `escalation`, `portal-mcp` |
| `knowledge` | looking up or recording a decision, lesson, runbook, post-mortem, playbook or daily line | all; scribe, incident-analyst | `portal-mcp`, `incident`, `decisions`; knowledge attachments (when available) |
| `browser-testing` | checking a UI change in the pilot browser; reproducing a phone bug; performance and accessibility; a login handoff | implementer, qa-verifier, ux-checker, perf-tester | `design-standard`, `ci-cd`, `safety`; the browser control plane, recordings, visual baselines, header injection, step mode (when available) |
| `design-standard` | building, changing or reviewing any user interface (a slot each project fills with its own standard) | implementer, qa-verifier, ux-checker, reviewer | `browser-testing`; the project's own standard |

Rules for every skill in the kit: no secrets or token-shaped strings, no scripts, hooks or tool pre-approvals, no network instructions; generic for any project, with project-specific material only in `references/example-*.md`. Kit skills are admin-owned and read-only to agents: a change is proposed on a ticket (or with `skill_propose`) and reviewed, and anything touching the charter's walls is a person's decision.
