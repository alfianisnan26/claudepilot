## 1. Summary

The portal gets one queue for work. A ticket says what needs doing: a type, a priority, a one-line summary, a Markdown description, tags, a status, who reported it and who it is assigned to. The assignee is either an agent session or a person. A person's request is an open ticket, and so is whatever an agent needs from a person (an approval, an answer, a decision), assigned to that person.

People work the queue in the portal's Tickets page: a list and a board with filters, a detail page with a timeline, and an action that starts a session for a ticket, optionally in a git worktree of its own, sending the ticket as the session's opening message labelled `ticket:<id>`. Agents work it through the Portal MCP: list and search, read, create, comment, update, claim the next ticket by priority and tags, and close with a summary. An agent changes only tickets assigned to it, and it can always create one.

Ticket text is untrusted input. It is stored with secrets removed and invisible characters stripped, rendered as Markdown without raw HTML, and handed to a model only labelled as untrusted text. A ticket never carries a credential and never grants an agent anything: it is a request, and the portal's guards decide what happens next.

## 2. Background and problem

- Work reaches agents by someone typing into a chat. The request lives in one transcript, nobody sees what is queued, and a second agent can't pick up what the first left.
- An agent that needs a person's decision can only stop and wait in its session. Nothing says what it needs or who should answer, and the answer isn't kept anywhere but the transcript.
- Several agents on several workspaces have no shared list of what is being done, by which session, in which worktree, and what came of it.
- Closing the loop is manual: after an agent finishes, a person has to remember to read the result and say it is done.

## 3. Goals

| ID  | Goal                                                                                                                                                                                                                                     |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G1  | **One queue.** Every request, from a person or an agent, is a ticket with a type, priority, summary, description, tags and a status, in one list.                                                                                        |
| G2  | **Agents and people both assign and work.** The assignee is an agent session or a person. An unassigned ticket is open to the agents; one assigned to a person waits for that person.                                                    |
| G3  | **Human requests are tickets.** What a person asks for, and what an agent needs from a person, is an open ticket. The page shows "Needs you" at a glance.                                                                                |
| G4  | **A session per ticket.** A person starts a session for a ticket from its page, optionally in its own worktree. The opening message is the ticket, labelled with its actor. The session page links back.                                 |
| G5  | **Agents over MCP, tightly scoped.** Tools to list, read, create, comment, update, claim and close. An agent changes only tickets assigned to it (or created by it), and sees only its own workspace's tickets and the unassigned queue. |
| G6  | **A timeline that can be trusted.** Every change is an entry: who (a person, a session, a token, the portal), what and when. Nothing is edited in place without leaving one.                                                             |
| G7  | **Untrusted text stays inert.** Ticket text can't carry a secret in, can't hide characters, and reaches a model only labelled.                                                                                                           |

## 4. Non-goals

- **A project-management suite.** No sprints, estimates, boards per project, SLAs, custom fields or workflows. Status, priority, type and tags are the model.
- **Per-user identity and permissions.** The portal has one shared sign-in. A person assignee is a label until per-user identity exists ([Portal MCP](portal-mcp.md) §12.5).
- **Automation that acts on a ticket by itself.** Nothing starts a session, assigns, or closes a ticket without a person's click or an agent's own tool call. A ticket in the agents' queue waits until an agent claims it. **Amended 2026-10-12** ([Triggers](triggers.md), owner decision O3): a trigger that a person created is the one exception. Its owner, limits and approval rules stand in for the click: it creates tickets (in the queue, or assigned to its owner) and may start a session on one, and does nothing else (it never reassigns, edits or closes).
- **An external tracker.** No sync with GitHub Issues, Linear or Jira. Links to them are text in a description.
- **Notifications outside the portal.** Push and email for "needs you" follow the Web app PRD's notification work (Q3). Answered 2026-10-12: [Web app & PWA](web-app-pwa.md) §11 sends the kind `human_request` (a ticket assigned to a person by an agent, a trigger or the portal) over Web Push, a signed webhook, Discord and Slack; email is not planned.
- **Files and images on tickets.** Text only in v1.

## 5. Users and stories

**Admin**: signs in to the portal; also the person tickets are assigned to. **Agent**: a Claude Code session in a workspace, with the portal's ticket tools through its own session token. **Script**: an admin's token over MCP.

| ID  | Story                                                                                                                                                                                                                                                                               |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| US1 | As an admin, I write down what I want done (a bug, a feature, a question) with a priority and tags. It joins the queue as an open ticket.                                                                                                                                           |
| US2 | I open the Tickets page and see what is open, in progress, blocked and waiting for me, as a list or a board, filtered by status, priority, type, tag or assignee.                                                                                                                   |
| US3 | I open a ticket, read its description and timeline, and start a session for it on a workspace, in a worktree of its own. The session opens with the ticket as its first message and I see "From ticket T-12" on it. The ticket shows the session, and the session shows the ticket. |
| US4 | An agent working a ticket comments its progress, marks it blocked when it needs something, and closes it with a summary. I see each step on the timeline.                                                                                                                           |
| US5 | An agent needs my approval to delete a branch. It creates a ticket of type approval assigned to me, with what it will do and why. I find it under "Needs you", answer in a comment, and close it. The agent reads the answer.                                                       |
| US6 | I leave several tickets unassigned with the tag `frontend`. An agent calls `ticket_claim_next` with that tag and gets the most urgent one, which is now assigned to its session and in progress. Two agents never get the same ticket.                                              |
| US7 | An agent in one workspace can't read or change another workspace's tickets, and can't change a ticket assigned to someone else.                                                                                                                                                     |
| US8 | A session ends without closing its ticket. The ticket still says in progress and shows that its session ended, so I can restart it or reassign it.                                                                                                                                  |
| US9 | I paste a ticket's text from an agent into nothing: whatever the ticket says, it can't make an agent run a command, because it is shown to the model as untrusted text and starting a session is my click.                                                                          |

## 6. Scope boundary

| Allowed                                                                                                                                                                                                             | Not allowed                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| People create, edit, assign, comment on, start sessions for, close, reopen and delete tickets in the portal.                                                                                                        | A ticket granting access: no token, credential, approval or permission is created or implied by one. An "approval" ticket records a person's answer; it does not itself approve anything. |
| Agents (a session's own token) create tickets, read the unassigned queue and their workspace's tickets, claim, comment on, update and close the ones assigned to them (or that they created and nobody else holds). | An agent changing a ticket assigned to another session or a person, reading another workspace's tickets, deleting a ticket, or reopening a closed one.                                    |
| A script with an operate-scope token does everything an agent may, without a workspace limit.                                                                                                                       | Starting a session from a ticket over MCP unless session control is on and the token is admin ([Portal MCP](portal-mcp.md) §13.3).                                                        |
| Ticket text of any length up to the caps (§11), as Markdown.                                                                                                                                                        | Raw HTML, images, scripts or secrets in ticket text. A message that looks like a secret is refused.                                                                                       |

## 7. Solution overview

```
  People (portal UI)                       Agents (Claude Code in workspaces) / scripts
  Tickets page: list, board, detail        Portal MCP: ticket_list, _get, _create, _comment,
  create, comment, assign, start session   _update, _claim_next, _close           (bearer token)
        │  /api/tickets                           │  /mcp   per-session agent token: own workspace + unassigned queue
        ▼                                         ▼
 ┌─────────────────────────────────────────────────────────────────────────────────────────┐
 │ Tickets service   one SQLite transaction per change; every change = a timeline entry     │
 │ rules: who may change what (§9) · text cleaned and redacted on the way in (§11)          │
 └───────┬───────────────────────────────────────────────┬─────────────────────────────────┘
         │ start session for a ticket                    │ session events (ended, state)
         ▼                                               ▼
   sessions adapter ──▶ ChatController: create(ticketId, worktree), send(actor "ticket:T-12")
```

The tickets module owns its tables, rules, REST routes and MCP tools. It reaches chat sessions through one adapter, so the rest of the module never imports the chat controller. A session carries the ticket's id (`ChatSession.ticketId`), and the ticket carries the session it is assigned to; neither is a foreign key across modules.

## 8. Functional requirements

### Tickets

- **FR1** A ticket has: an `id` (`T-<n>`, counting up from 1), a `type` (`task`, `bug`, `feature`, `question`, `request`, `incident`, `approval`, `chore`), a `priority` (`urgent`, `high`, `normal`, `low`), a `status` (`open`, `in_progress`, `blocked`, `in_review`, `done`, `wont_do`), a one-line `summary` (at most 140 characters), a Markdown `description` (at most 20,000), up to 10 `tags`, a `source` (`human`, `agent`, `system`), a reporter, an assignee, an optional workspace, and timestamps. Defaults: type `task`, priority `normal`, status `open`.
- **FR2** Tags are lowercase `[a-z0-9][a-z0-9._-]*`, at most 30 characters. Entering `Front End` stores nothing and says why; the UI offers the existing tags.
- **FR3** The reporter is who made it: a person in the portal (`ui`), an agent (`session:<id>`, with the workspace and session its token is bound to), a script through an admin's token (`portal-mcp:<token id>`), or the portal itself (`system`). `source` follows: `human`, `agent`, `system`. It never changes.
- **FR4** The assignee is nobody, an agent session (`session`: a chat session id), or a person (`user`: a label, `admin` by default). Nobody means the ticket is in the agents' queue. A person assignee means it waits for a person. Assigning moves nothing else: status is changed on its own, with its own entry.
- **FR5** A ticket may name a workspace (`workspaceId`): where the work happens. A ticket made by an agent gets its token's workspace. A ticket with no workspace belongs to the shared queue. When a session works the ticket in a worktree, the ticket shows the worktree's branch and folder, read from the session.
- **FR6** Closing is a status of `done` or `wont_do` with a closing summary (at most 2,000 characters), recorded as a timeline entry and on the ticket. A closed ticket is read-only for agents. A person may reopen it to `open`; the entry says so.
- **FR7** Every change is a timeline entry in the same transaction: `created`, `comment`, `status`, `assigned`, `priority`, `type`, `summary`, `description`, `tags`, `workspace`, `session_started`, `session_ended`, `ci`, `closed`, `reopened`. An entry names its actor (`ui`, `session:<id>`, `portal-mcp:<token id>`, `ci:<run id>`, `ticket:<id>` for a session the ticket started, `system`) and holds the from and to of what changed, or the comment's text. Entries are never edited or deleted, short of deleting the ticket.
- **FR8** A person can delete a ticket (with its timeline) after a confirmation. Agents can't.

### What agents may change

- **FR9** An agent (a per-session token) may: list and read tickets in its workspace or with no workspace; create a ticket (its workspace is forced to the token's); and change, comment on or close a ticket only when it is **assigned to its own session**, or **it made the ticket and nobody holds it** (unassigned, or assigned to a person). Anything else is `FORBIDDEN` naming the rule (a ticket in another workspace is `NOT_FOUND`). It can't delete, can't reopen, and can't change `source` or the reporter.
- **FR9a** (T-270, 2026-10-14) A ticket held by **another session that has ended** is not stuck. An agent may comment on, change and close it when that session is in the **same workspace** and either is in the agent's **lineage** (its `continued_from` chain back) or has **no live successor** (nothing continuing it is live: an orphan). The rule is one function, `canActForEnded` in `tickets/authz.ts`; the service gathers the facts. Each such write leaves an audit row `ticket.acted_for_ended` naming the acting session, the ended one and why (`lineage` or `orphan`). Never for a ticket a live (or interrupted) session holds, a person holds, or of another workspace: those keep the FR9 refusal, whose text now points at `ticket_adopt`. A session missing from the database does not count as ended.
- **FR9b** (T-294, T-397, 2026-10-15) A **crew worker** (a live session with a lead, `parentId`, started by `session_spawn`) may **comment** on a ticket it does not hold in four cases: (1) a session holds it that is its **lead**, or a session continuing its lead (`continued_from` back from the holder reaches the lead, so a restarted lead's tickets still take its workers' reports; the lead's own lead is not followed); (2) it is the ticket its **spawn named** (the session's `ticketId`, `session_spawn` `ticket`) and **nobody holds it** (the lead started the worker before claiming); (3) `crew_ticket` (T-969): a crew mate (same lead) holds it; (4) `crew_queue` (2026-10-18): **nobody holds it** and it is in the **worker's own workspace** (long-lived lanes, D-70, work many tickets, so their reports on unassigned tickets no longer go through the coordinator). `crew_queue` grants a comment only, never an attachment; `ticket_comment` is limited to 120 an hour per token. A comment only: never a change, a close, a claim or an adoption. The spawn's ticket held by a person or by another session is refused, so a lead cannot open another's ticket by naming it. The rule is one function, `canWorkerComment` in `tickets/authz.ts`. The timeline entry is the worker's (`session:<worker>`), and each such comment leaves an audit row `ticket.worker_commented` naming the worker, its lead, the holder and why (`lead_ticket`, `spawn_ticket`, `crew_ticket` or `crew_queue`; `lead_peer` and `peer_worker` under FR9g). An ended worker, a closed ticket and every other case keep the FR9 refusal with its text. Reading needs nothing new: a worker runs in its lead's workspace, so FR9 already lets it read these tickets. External MCP tokens are unchanged (FR10).
- **FR9c** (D-62, T-483, 2026-10-15) **An agent does not put a ticket on a person.** An agent's own token (a chat session or a crew worker) is refused with `FORBIDDEN` and the D-62 text ("D-62: agents do not assign tickets to a person. Decide by the written default …") when its `ticket_create` or `ticket_update` leaves the ticket on a person (`user`, `user:<name>`) without a tag listed in `tickets.agentAssignUserTags` (Settings > Tickets, comma separated, default `production`; empty: never), and its change is what puts it there: a new ticket, a move to a person or to another person, or removing the last allowed tag from a ticket a person holds. A ticket already on a person that the change leaves so is not judged again. A person, the page, an admin's token and a trigger a person made are never refused. The rule is one function, `canAgentAssignUser` in `tickets/authz.ts`; each refusal leaves an audit row `ticket.agent_assign_refused` (session, lead, tags, the allowed tags). Every allowed assignment to a person by an agent (through an allowed tag) or by an admin's token acting for a session leaves an audit row `ticket.agent_assigned_person` (ids, actor kind, the allowing tag; no ticket text). The setting is changed only by the owner (the settings route; moving it off `production` asks to confirm); no agent tool writes it. No other agent path assigns a person (claim, adopt, bump, the orphan sweep and continuations assign sessions only).
- **FR9d** (D-62, T-527, 2026-10-15) **An agent does not put a ticket on the owner checklist on its own.** The tag `owner-checklist` lists a ticket on the owner's Needs you without an assignee, so it gets the same rule as FR9c: an agent's own token is refused with `FORBIDDEN` and the D-62 text ("D-62: agents do not put a ticket on the owner checklist (tag owner-checklist) on their own. Decide by the written default …") when its `ticket_create` or `ticket_update` ADDS `owner-checklist` without a tag listed in `tickets.agentAssignUserTags` (default `production`). Removing the tag is always allowed; a ticket that already carries it may be changed as long as the change does not add it. A person, the page, an admin's token and a trigger are never refused. The rule is one function, `canAgentTagChecklist` in `tickets/authz.ts`; each refusal leaves an audit row `ticket.agent_checklist_refused` (session, lead, tags, the allowed tags). Every path that sets tags (the two tools and the two routes) goes through the service's `create` and `update`, where the check sits next to FR9c's. Needs you counts the tag only with an allowed tag or when a person added it (below).
- **FR9f** (2026-10-18, T-84 c11534) A crew **lead** (a live agent session with at least one live worker) may **hand off** a ticket of its own workspace: the ticket is open and held by nobody, by the lead, or by one of its live workers; the new holder is the lead, one of its live workers, or nobody (the queue); only `assignee`, `status` and `priority` change (never a close: closing stays `ticket_close`). A person's ticket, another crew's, the shared queue's, another workspace's and an ended holder's (FR9a) keep their rules. Each hand-off is audited once stored as `ticket.lead_assigned` (lead, from, to). The rule is `#leadMayAssign` in `tickets/service.ts`.
- **FR9g** (D-85, 2026-10-18) **Peer leads** comment on each other's tickets: a live top-level agent session may comment on a ticket held by another top-level session in the same workspace (live or ended since T-1839) when both are in one group of the owner-only setting `tickets.leadPeerGroups` (groups by `;`, session ids by `,`; a continuation of a listed session counts as it). Bound to ids, never to a title an agent could rename (review 2026-10-18). No change, claim or attachment; a comment is audited as `ticket.worker_commented` with why `lead_peer`. **T-1839 (2026-10-20):** a peer lead may also **close**, and both comment and close reach a ticket held by a **worker** of a peer lead: the holder's crew root (the top of its `parentId` chain) must be in the actor's group, its lineage counted back and forward (`continued_from`), so a lane started before its lead was continued still belongs to the listed successor. A broken chain (a session missing, a cycle, deeper than 20) refuses. The actor must be a live top-level session (a worker never), in the holder's workspace. Each such close leaves an audit row `ticket.lead_peer_closed` (acting session, holder, holder's lead, outcome). A lead outside the group, a person's ticket and FR36 verdict rules are unchanged. The rule is `canPeerLeadAct` in `tickets/authz.ts`. **T-2011 (2026-10-22, D-93 cross-unit QA):** a **QA or review worker** (its agent name ends in a whole role word: `qa`, `qa-verifier`, `verifier`, `reviewer`, `review`, with at most one prefix part) **started directly by a lead of a peer group** (its `parentId` is that lead or a predecessor or continuation of it; the name is the spawner's choice, so a QA-named child of any other worker gets nothing) may **comment** on a ticket held by a session whose crew root is in the same group: a peer lead, a peer lead's worker, or its own crew. A comment only (no close, change, claim or attachment), audited as `ticket.worker_commented` with why `peer_worker`; an implementer worker, a worker of a lead outside the group and a broken chain are refused, and a ticket it may not see is the same not found. Its verdicts (`ticket_verdict`, `ticket_verdict_batch`) need no holder grant: FR36 decides them per ticket, unchanged (an author, the lead, a session an author started stay refused). The rule is `canPeerWorkerComment` in `tickets/authz.ts`.
- **FR10** An admin's token with `operate` scope may do what a person may in the UI except delete and start a session. `read` scope only reads.
- **FR11** Which session is calling: an agent's token carries it, verified by the portal and never taken from arguments (a `session_id` that names another session is `FORBIDDEN`); the audit row and the timeline say `session:<id>`. An admin's token that acts as a session passes `session_id`, which must be a live session; a call that needs "me" (claiming, assigning to me) with none named is `SESSION_REQUIRED`.
- **FR12** An agent creating a ticket for a person (an approval, a question) assigns it to `user` only with an allowed tag (FR9c: default `production`); otherwise it is refused with the D-62 text and decides by the written default. It may later comment on it and close it (FR9), and read the person's comments.

### Claiming

- **FR13** `ticket_claim_next` picks, among tickets that are `open`, unassigned and visible to the caller (FR9), those that have every tag asked for and one of the types asked for, orders them by priority (urgent first) then by age (oldest first), and in one transaction assigns the first to the calling session and moves it to `in_progress`. Two callers never receive the same ticket. With none left it returns nothing, not an error.
- **FR14** Claiming is the only way an agent acquires a ticket it did not create. A person can assign any ticket to any session or person.

### Sessions

- **FR15** **Start a session** (people only, from the ticket's page): pick a running workspace, optionally a Claude on it, and whether to use a worktree of its own. The portal creates the session with `ticketId` (and the worktree when asked), assigns the ticket to it and sets it `in_progress`, then sends the opening message with the actor `ticket:<id>`. The dialog shows the exact opening message first. A ticket that came from an agent shows who wrote it and from which workspace.
- **FR16** The opening message is the ticket: its id, type, priority, summary, tags, description, who reported it, the id of the session now assigned, and a closing line saying that if the portal's ticket tools are available the agent should report with `ticket_comment` and finish with `ticket_close`. It is plain text built by the portal; the ticket's own words are inside it, labelled as the ticket's. The transcript shows it as a portal message from the ticket, never as something the person typed ([Chat sessions](chat-sessions.md) FR14).
- **FR17** A ticket shows the sessions that worked it (those whose `ticketId` is its id), each with its state. The session page shows its ticket as a chip linking to it.
- **FR18** When a session assigned to a ticket ends while the ticket is `open`, `in_progress` or `blocked`, the ticket keeps its status and gains a `session_ended` entry with the reason. The page flags it ("Its session ended") so a person can restart it or reassign it. Nothing is closed or reassigned by the portal at that moment.
- **FR18a** (T-270) Tickets follow the track. A session created with `continuedFrom` (chat sessions §10.4) takes, in the transaction that creates it, every unfinished ticket (`open`, `in_progress`, `blocked`, `in_review`) held by the ended predecessor and its ended predecessors: an `assigned` entry each with actor `system` and `continued: true`, as migration 772 wrote them; the status stays. Closed tickets keep their assignee (who did the work). `ticket_adopt` does the same on request for an ended session of the FR9a rule: the entries carry the caller, `adopted: true` and why, and one `ticket.adopted` audit row lists the ids. What a continuation or an adoption missed, the orphan sweep (FR18b) moves by itself.
- **FR18b** (T-270 layers 2 and 3) **Orphans fall back by themselves.** An **orphan** is an unfinished ticket held by a session that is dead: `ended`, archived, or no longer in the portal (`interrupted` is live: it can be woken). It is derived when read, not stored: `Ticket.orphan` is `{since, sessionId, why}` (`why` `ended`, `archived` or `missing`; `since` the time the portal saw it dead, null until the sweep has looked), the list filter `orphan` and the count `counts.orphans`. The **orphan sweep** (`tickets/orphans.ts`, the rules in the service) runs once a minute with jitter, one pass at a time, at most 200 moves a pass; its last pass and the time each dead session was first seen dead are in `portal_meta` (`tickets:orphans`), so a restart neither resets nor skips the delay. When a session has been dead for `tickets.orphanAfterMin` (Settings > Tickets, default 3 minutes), each of its unfinished tickets moves, in its own transaction, checked again inside it, in this order: **(a)** the live session whose `continued_from` chain reaches the dead one (the nearest, then the latest active), else a live session of the **same workspace** whose title has the same prefix up to its first ":" ("Orchestrator: ClaudePilot dev"; a title without ":" matches nothing); only when the ticket is in that workspace or the shared queue; **(b)** otherwise back to the agents' queue, unassigned, with one system comment "Its session ended: back in the queue."; the status stays (`in_review` stays `in_review` for a verifier, `blocked` stays) except `in_progress`, which becomes `open`; description and comments stay; **(c)** a ticket a person holds is never touched, and the sweep never assigns to a person. Each move is one `assigned` entry (actor `system`, `fallback: true`, `reason` `lineage`, `title` or `queue`, `holder` the why) and one `ticket.fallback` audit row (`from`, `to`, `reason`). A session back to live within the delay (in-place recovery, T-136 keeps its id) keeps its tickets; a later end starts the delay again. The sweep creates no ticket (no needs-a-person request) and sends no notification. The page shows an orphan with a red "Session ended" (or "archived", "gone") badge, a line on the ticket "Its session ended · 2m ago" with an ⓘ, and an "Orphans" chip with its count, first in the chip row (seen on a phone without scrolling sideways), while there are any; the timeline reads a move as "Portal moved it to the session that continues it" (or "to the live session of its track", or "put it back in the queue"). Not built: the "Needs you" entry for an orphan the fallback could not resolve (T-146 does not exist yet; today the queue path always resolves one). Known gap: `ticket_claim_next` takes only `open` tickets, so an `in_review` or `blocked` ticket back in the queue is picked up by someone assigning it, not by a claim. A session missing from the database is dead for the sweep, though not for the FR9a rule (which stays narrow).

### Bump (T-28, owner 2026-10-13)

- **FR28** **Bump** (a person on the ticket's page or its row ⋯; a script with `ticket_bump`): push an open ticket into a session that is already running. The picker offers the ticket's assigned session first, then the live sessions of its workspace (every workspace's for the shared queue), each with its title and state; a session that ended, waits on an approval, or works in another workspace is not offered, or shown greyed with why. Two ways, explained in one ⓘ: **Prioritise** (the ticket is assigned to that session and set `in_progress`; the message goes in with the chat queue priority `next`, so it steers the running turn) and **Ask** (a question: nothing about the ticket changes; the message goes in as `later` and asks for an answer in the ticket). An optional note of one line (at most 200 characters, cleaned like any ticket text, never a credential). Start session stays as it is.
- **FR29** The session gets a portal message from the ticket (actor `ticket:<id>`, label `T-<n>`, so the transcript says "From ticket T-12") in the opening message's style: who bumped it and how, the ticket's type, priority, tags, summary and link, the note, the description fenced as the ticket's words (cut at 4,000 characters, pointing to `ticket_get`), and what to do (Prioritise: work on it and report with the ticket tools; Ask: answer with `ticket_comment`, do not take it on). A session asked about a ticket may comment on it for a day even when FR9 alone would refuse (another session or a person holds it); it may not change or close it.
- **FR30** Every bump is a `bumped` entry on the timeline (who, which session and its title, how, the note as its text), after the `assigned` and `status` entries of a Prioritise, and before the message is sent; a send that fails leaves a note from the portal and says so. Limits: 10 bumps of a ticket and 20 bumps into one session an hour (`RATE_LIMITED`). A bump is written to the platform audit (`ticket.bumped`: ticket, session, mode, whether there was a note; never the note's words); over MCP the call is in the Portal MCP audit too. Who may: a person, or an admin's token of operate scope or more; never an agent's token, a read token or a trigger. The route and the tool check the seam first: operate on the ticket and on the session (`tickets/authz.ts`); another person's session is the same 404 as a missing one, and the picker lists only sessions the person may operate.
- **FR31** The session page's info shows the tickets bumped into it beside its own ticket, each as a chip with how ("T-12 · Ask"), linking to the ticket.
- **FR32** The picker, the two ways and the message's shape are shared (`apps/web/src/components/BumpDialog.tsx`, `apps/server/src/chat/bump.ts`, `packages/contracts/src/bump.ts`), so a CI run's Bump (T-32 part 2) offers the same sessions, ways and text.

### Verdicts (T-325 S1, 2026-10-15)

- **FR36** A QA or review result is a **verdict**, a row and not words in a comment: `role` (`qa` or `review`), `verdict` (`pass` or `fail`) and the **full 40-character commit sha** that was verified (an abbreviation is refused: it may name more than one commit). Rows are never edited; the latest verdict of a role on a commit wins, so a later `fail` voids an earlier `pass` of the same commit. Recording leaves a timeline comment (who, role, verdict, sha) and an audit row `ticket.verdict`; a refusal that reached the rule leaves `ticket.verdict_refused` (code and role, never text).
- **FR36a Who may record.** One rule, `canRecordVerdict` (`tickets/verdicts.ts`), the service gathers its facts. A person in the portal may. An agent may only as a session whose agent name says QA (`qa`, `verifier`) or review, and only for its own role. Never: the **author** (the holder, its `continued_from` ancestors, every session ever assigned the ticket, every session started on it), the **lead** (the parent of any of those), an implementer, a lead or any session with no QA or review agent, an admin's token (even acting for a session), a trigger and the portal itself. **Nor anything an author started** (T-325 S1b): a session's agent name is chosen by whoever spawned it, so the rule walks the caller's spawn chain (its parents and the sessions it continues, up to the root) and refuses `descends_from_author` when any of them is an author, whatever the caller is named. The one author allowed in that chain is a holder that **leads** the work (the parent of another author, not itself started on the ticket) and its lineage, so an orchestrator holding a ticket can send its own QA worker; an implementer that holds a ticket leads nobody, so a QA it spawns is refused. **T-1652 (2026-10-20):** a **past holder** that is an ancestor of the current holder by `parentId` (a lead that handed the ticket to its own worker) and was not started on the ticket, nor any session it continues, leads the work too, so its QA children may record; the builder (the holder started on it), a past holder started on it, a past holder that is not the holder's ancestor and a parent chain with a session nobody can look up are still refused. Residual risk, decided on T-325: a root session that holds a ticket, is not started on it and has a worker on it looks like an orchestrator even if it also writes code. A ticket the caller may not see is the same not found as a missing one; a rule refusal on a visible ticket is `FORBIDDEN`.
- **FR36b A moved branch never passes.** `evaluateVerdicts(verdicts, head, need)` counts only verdicts on exactly `head`; a verdict on any other commit is `stale` and does not count, and no row ever expires on its own (the reader compares). `need` is the roles that must pass (default `qa`); an empty list is never a pass. The planner of S2 and any person read through `verdictStatus`. Tested with a mutation: with the comparison replaced by "any commit", the stale-PASS assertion fails.
- **FR36c A QA or review lane that holds a ticket is warned about** (T-1608). Every session ever assigned a ticket is its author (FR36a), so a QA or review lane that holds one can never record its verdict. The assignment is not refused (a QA lane may hold QA work: a test plan, a perf suite), but when an agent puts a ticket on a session whose agent has a verdict role (`verdictRoleOfAgent`: QA or review), on create, update or a lead's hand-off (FR9d), or such a session claims one (`ticket_claim_next`), the tool result carries `warning` ("<session> is a QA/review session: holding this ticket makes it an author of its work, so it can never record a verdict on it. If you meant it to verify, keep the ticket and brief the lane by ticket id.") and the timeline gets the same text as one Portal comment (`data.verdictLane`). A person in the portal gets neither. Adopting an ended session's tickets (FR9a) and the orphan sweep (FR18b) are not judged: they move tickets the lane already held.
- **FR36d A QA batch, a verdict per ticket** (T-1987, D-93). QA runs one pass over a batch branch (Konfersi `qa/batch-<date>-<n>`, ClaudePilot `batch/<date>-<n>`) and records one verdict per ticket, each on that ticket's own head, with `ticket_verdict_batch`: 1 to 20 items `{id, commit, verdict, role}` and one shared `evidence` `{job_id, batch_branch, note}`. Each item goes through `recordVerdict` exactly as `ticket_verdict` does: the FR36a rule (author, lead, anything an author started, T-1652 past holders, role, full sha) and the same not found for a ticket the caller cannot see. Items are independent: a refused one comes back as `{ok: false, error: {code, message}}` (the words `ticket_verdict` would answer) and the rest are recorded. The evidence is checked once before any item, like any ticket text (hidden characters out, a credential-shaped value refuses the whole call; a job id and a branch are plain names; at most 120, 120 and 500 characters). It is kept with every verdict of the call (`ticket_verdicts.batch`, JSON `{jobId, branch, note}`, migration 795), in its timeline entry (`data.batch`; its sentence names a 12-character sha and "in a batch", the chips carry the branch and the job, `data.commit` the full sha) and in its audit row `ticket.verdict` (one per ticket). A verdict recorded alone has none. The ticket page shows a batch verdict's entry with a "batch <branch>" chip and the job id chip (plain text; the note is their title). The flow watchdog reads a ticket as **in a live batch** when a comment or CI entry after its newest verdict names a batch branch (`liveBatchOf`), and does not ask for it again (flow-watchdog PRD).
- **FR36e One merge truth: the PR, its head and its state** (T-2014, 2026-10-22). The merge gate is the only one that knows a pull request's head (it reads the forge); the portal knew only the newest commit it had heard of, so the flow watchdog counted tickets the gate would not merge. `ticket_merge_status` records, per ticket and repo, `{repo, pr, pr_head, state, reason?}`: `state` is `ready` (open, the verdicts it needs on that head), `merged`, `conflict` (needs a rebase), `waiting` (verdicts on that head not yet in), `no_pr` (no PR open; `pr` and `pr_head` left out) or `failed` (tried and could not merge; `reason` says why, at most 300 characters, untrusted text). `pr_head` is a full 40-character sha, stored lowercase; every state but `no_pr` needs `pr` and `pr_head`. **Who may record:** only an agent's own token, and only the **merge-gate lead of a flow program** whose tag the ticket carries (the program's configured merge gate when it is a lead of the program's group, else the group's first lead; a program with no group set counts each group's; a continuation of the gate counts as it) or a **live worker that lead started directly** (its `parentId` is the gate or a predecessor or continuation of it). Another lead, a peer, a worker's worker, a person's token and any other agent are refused (`FORBIDDEN`, audited `ticket.merge_status_refused`); a ticket the caller cannot see is the same not found. The gates come from `flow.programs` and `tickets.leadPeerGroups`, read on every call (`mergeGatesOf` in `flow/programs.ts`). A record is a row, never edited (`ticket_merge_status`, migration 796); the newest row of a repo is its state; each is audited `ticket.merge_status` (ticket, repo, PR, head, state, gate or gate_worker, session). **Read:** `ticket_merge_status` without `state`, `GET /api/tickets/:id/merge` (declared view on the ticket) and `merge` in the ticket's detail give the latest record per repo, newest first. The ticket page shows one chip per repo, "api#12 · ready" (the whole repo, the head, when and the reason in its title). The flow watchdog judges a QA PASS on `pr_head`, skips a ticket merged everywhere, and tells the unit lead about `conflict` and `no_pr` (flow-watchdog PRD).
- Not built here: the integrate push door (S3) waits for a person's decision on the charter rule and a token (T-325, comments 5547 and 5549); a REST route and a UI for people (the service already accepts the person).

### Buckets (T-1098, owner 2026-10-18)

- **FR37** A **bucket** is a project of tickets: a key of 2 to 6 capital letters (`KONF`, `CP`, `TB`, `PILOT`) that prefixes its tickets' ids, a name, a description, a default workspace, default tags, an optional knowledge vault and its own number counter. Every ticket is in exactly one bucket and keeps it (moving a ticket between buckets is not built). Its id in the bucket is `<KEY>-<n>` (`KONF-12`), numbered from 1 in creation order; the portal shows that id.
- **FR38** `T-<n>` stays the ticket's stable id and a **permanent alias**: the primary key is still the global number, and every place that takes a ticket takes both forms (any case for the key): the routes (`/api/tickets/KONF-12` and `/admin/tickets/KONF-12`), every ticket tool, CI's branch (`ticket/KONF-12-slug`) and trailer (`Ticket: KONF-12`, resolved to `T-<n>` by `find`), `claimNext({ id })`, the search box (`q` that is a reference also finds that ticket) and the palette. Events, sessions, audits and CI keep writing `T-<n>`, so nothing that names one breaks: a ticket argument that is STORED is turned into `T-<n>` where it enters (a session's ticket through `create`, `setTicket`, `session_create` and `session_spawn`; a lab draw), and the filters by ticket (sessions, CI runs) take either form.
- **FR39** A new ticket's bucket (T-2881 order, added 2026-10-28; why: agents filed Konfersi tickets through `ticket_create` without `bucket`, they fell through to `PILOT`, and 214 were moved by hand): the one named (`bucket` on the request or on `ticket_create`; it always wins); else the one bucket the ticket's own tags point to by the setting `tickets.bucketRoutes` (owner only; rules `KEY: tag, tag, prefix-*` split by `;`; default `PILOT: claudepilot, program-claudepilot; KONF: konfersi-migration, area-*; TB: tradingbot`; an exact tag beats a `prefix-*` pattern, because the portal's own tickets carry `area-*` tags too; two buckets tied on the deciding kind, or a bucket that does not exist or that the agent may not file in, decide nothing); else the bucket of `parent` (an epic or parent ticket, `T-12` or `KONF-3`, one the caller can see; it is not stored, only its bucket is used); else the one bucket whose default workspace is the ticket's (or the agent's) workspace; else the bucket of the ticket the calling session, then its lead, works on (`ticketId`); else `PILOT`. The reason (`named`, `tags`, `parent`, `workspace`, `session_ticket`, `lead_ticket`, `default`) is kept on the `created` timeline entry (`bucketReason`), and `ticket_create` returns `bucket: { key, reason, why }` and names it in its summary (`Created KONF-12 in KONF (tags).`). T-3069 (human request, 2026-10-30): the `ticket_create` description tells agents to file by what a ticket is about, not where they run: "pipeline, portal, allow-list, brief or harness problems go to PILOT, whatever workspace you are in" (name `bucket` PILOT or tag `claudepilot`); `portalTools.test.ts` checks the sentence. A bucket's default tags are not matched by the rules (they are added after the bucket is chosen). Not built: a stored parent link, and the lead's flow program as its own step (the session and lead ticket steps stand in for it). A bucket's default tags are added, and its default workspace is used when the request leaves `workspaceId` out (an explicit null keeps the shared queue). Numbers are handed out by a database trigger inside the insert's own transaction, so concurrent creates never share or skip a number.
- **FR40** A bucket is an object of the authorization seam (`ticket_bucket`; owner `owner_id`): **view** to see it and its tickets, **operate** to file a ticket in it, **manage** to change it. Every `/api/tickets/:id` route checks the ticket's bucket (view to read, operate to change) and answers a hidden one exactly like a missing ticket (the same 404 and text); lists leave its tickets out. The tools check `bucket` at dispatch (operate for `ticket_create`, view for `ticket_list`) with the text "No such bucket.", the same as a missing one. T-1857: the service's one read path asks `view` on the ticket's bucket too, for agents, admin and manager tokens (their seam actor, a manager being its person) and a person's list: every tool that names a ticket (`ticket_get` by T-<n> or key, comment, update, close, attach, verdict, `ticket_claim_next` by id, adopt) answers a hidden one as "No such ticket.", the same as a missing one, and no list, search, total, count, tag count or claim includes it. The single owner holds every bucket, so nothing changes for them.
- **FR41** Agents: an agent files in, lists and reads only buckets with no default workspace or with its own workspace as default (another workspace's bucket is "No such bucket."). The lead and crew rules (FR9b, FR9d) are unchanged. Only a person or an admin token (not the General Manager's) makes or changes a bucket; `ticket_buckets` lists the ones the caller may use.
- **FR42** The queue filters by one bucket (`?bucket=KONF`) and `counts.byBucket` gives the unfinished tickets per bucket; the New ticket dialog picks a bucket (Auto by default); a Buckets dialog on the queue makes and edits them. Not built yet (follow-up): Home cards and scorecards per bucket, deleting a bucket with tickets other than by a merge (FR44), the lab reading a bucket key from a brief's text (it reads `T-<n>` only), and scoping the agents' read tools by bucket.

- **FR43** (T-1967, owner 2026-10-21: "PILOT and CLAUDEPILOT should be consolidated") A ticket **moves** to another bucket: `PATCH /api/tickets/:id { bucket }`, `ticket_update` `bucket`, or the Bucket select on its page. It takes the target's next number; every key it had stays an **alias** (`ticket_key_aliases`, migration 48), resolved everywhere a key is (routes, tools, trailers, branches, search); `T-<n>` never changes. A bucket's counter only grows, so no key is handed out twice (a bucket made again under a merged key counts on after every number the merged bucket handed out, a deleted ticket's included: its counter is kept in `ticket_buckets_retired`). The move needs operate on both buckets (the same 404 for one out of reach), the caller's right to change the ticket (an agent only into a bucket of its workspace; a crew lead's hand-off cannot move it), is a `bucket` timeline entry `{ from, to }` and an audit row `ticket.bucket_moved`. The counter and the ticket change in one transaction, so a create racing a move never shares or skips a number.
- **FR44** **Merge** (owner only: manage on the platform's settings and on both buckets): `POST /api/tickets/buckets/:key/merge { into, name?, description? }` or Merge into in the Buckets dialog. Every ticket of the bucket moves into `into` in creation order with `into`'s next numbers, its keys stay aliases, and the bucket is deleted, in one transaction; audited `ticket.bucket_merged`. `name` and `description` rename the target; merging `CP` into `PILOT` names it "Pilot", "ClaudePilot" unless given. **Bulk moves** (owner only): `POST /api/tickets/bucket-moves { moves: [{ id, bucket }] }` (1 to 500), each on its own transaction, answers each ticket's `{ id, from, to, ok }` or `{ id, ok: false, error }`; a bucket the caller may not operate reads as a missing ticket.

### Timeline (T-119, owner 2026-10-13)

- **FR45** A ticket's **flow** is derived from its events, never stored twice: `ticketFlow` (`apps/server/src/tickets/ticketFlow.ts`, pure, "now" passed in) turns the `status`, `closed` and `reopened` events into **spans** (state, start, end or null while running, duration, who moved it there, why) and the other events into **markers** (assigned, claimed, bumped, a person's comment, priority, tags, CI, waiting). Events are read in time order whatever order they arrive in; an unreadable time or an unknown status is ignored; a ticket with no status event is one span from its creation in the status it has; a reopened ticket has several spans of one state; a closed state (done, wont_do) is a point at the close and the next span starts at the reopen. **Waiting** is the tag `needs-a-person`: while it is on, that stretch is a `waiting` span in place of the status span it covers; a close ends it and a reopen with the tag still on starts it again. `clipFlow` keeps the spans that touch a window (a running one up to now) and the markers inside it; `state` and `totals` stay over the whole life.
- **FR46** `GET /api/tickets/timeline` (§10) answers the tickets whose life overlaps a window, oldest number first, each with its clipped flow, its key (`KONF-12`), bucket, priority and assignee. The scale bounds the window: minute at most 24 hours (6 by default), hour 14 days (3), day 180 days (30); a longer one is a 422 that names the maximum. It takes the list's filters (bucket, status, priority, type, tag, assignee, workspace, `q`; closed tickets are in unless `status` says otherwise), pages by keyset on the number (50 by default, 200 at most, the cursor bound to the caller, the filter and the window), and checks every row and its bucket with `view`: a bucket filter the caller may not view is the same 404 as a missing bucket, and a hidden ticket is in no page and no cursor. Computed on read: the events of a page come in one query on the index `ticket_events (ticket_number, at)` (migration 794). An answer is kept 5 seconds per viewer and dropped as soon as any ticket or event is written.
- **FR47** The Portal MCP tool `ticket_timeline` (§12) reads the same service with the same checks, for an agent to reason about flow.
- **FR48** The Tickets page has a third view, **Timeline**, next to List and Board (`?view=timeline&scale=minute|hour|day`, the view and the scale also remembered on the device). It shares the queue's filters (bucket, status chips, Needs you, Unassigned, priority, type, tag, search); its first chip reads All (closed tickets included) and the chips show no counts, since those are the queue's, not the window's. One row per ticket: a pinned left column with the key, the priority mark and the assignee's initials (the title too from 600 px), the axis on top with ticks that follow the scale, thinned to a round step at least 40 px apart (every 10 minutes at the minute scale) and labelled only where the whole label is in view, never half under the pinned column or past the edge (T-1988), weekends shaded at the day scale and nights (22:00 to 06:00) at the hour scale, a now line, one bar per span in its state's colour (each state its own; Done is a violet token of its own, apart from In progress's green in both themes, T-1988) with its letter and, for blocked, waiting and won't do, a pattern (colour is never the only cue; a legend is always shown), a diamond at a close, and small marks for markers. A tap or Enter on a bar opens its details (from, to or "now (running)", duration, who with a link to the session, why, what happened in it, Open ticket) as a popover from 640 px (kept 12 px inside the page's content edge, never on a classic scrollbar, T-1988) and a sheet below; arrow keys move between bars, Esc closes; the row label opens the ticket. The chart pans sideways inside its own box and opens at now; the page never scrolls sideways. 200 tickets a page with More; a live change (batched, at most every 1.5 s) or each minute reads page 1 again, and rows keep their number order, so the ones on screen hold still. The view is its own lazy chunk.

## 11. Security requirements

- **Ticket text is untrusted.** On the way in, every text field has escape sequences, control characters, bidirectional and zero-width characters and Unicode tag characters stripped, and credential-shaped text refused: a ticket or comment that contains a key is a 422 naming the field, and nothing is stored (the same shapes as [Portal MCP](portal-mcp.md) §14.3). Over MCP the same refusal is `SECRET_IN_ARGUMENT`.
- **On the way out to a model** every ticket text (summary, description, comments, closing summary, labels) is returned as `{"untrusted_text": …, "source": "ticket:human" | "ticket:agent" | "ticket:system"}`, capped, never inside a tool description or the server's instructions. The opening message of a session (FR16) frames the ticket's words the same way in prose.
- **Rendering.** Markdown without raw HTML, images shown as links, links open in a new tab with `noopener noreferrer nofollow`; the same renderer the chat uses.
- **A ticket grants nothing.** No path from ticket text to a permission: sessions started from a ticket follow the session rules (eligibility, folder trust, no bypass over MCP); an approval ticket's answer is a comment a person wrote.
- **The agent rules are enforced by the server** (FR9), on every call, from the token's workspace and the ticket's assignee, never from what the caller says about itself. Claiming is one transaction.
- **Audit.** Over MCP every call is in the audit trail with its token and actor; ticket changes carry the actor in the timeline entry (`session:<id>` for an agent).
- **Limits.** Text caps (FR1), the creation limits (FR20), the MCP rate limits ([Portal MCP](portal-mcp.md) §14.5).
- Tests: injection text in every field of a ticket comes back stripped and labelled; a secret in any field is refused; the authorization matrix (no token, read scope, an agent token of another workspace or session, one after its session ended, another session's ticket, a closed ticket) for every tool; two concurrent claims never return the same ticket.

### 12.1 Short results (T-282)

A tool result is written into the agent's context once and read again on every later request of that session, so a
long one is paid for many times. Measured on 2026-10-14 from the session tapes: `ticket_get` was 5.5 percent of all
tool result characters; 92 `ticket_get` calls in one orchestrator's tapes averaged 6,680 characters (p90 14,669),
and T-277 read with `events: 40` was 16,401 characters.

- `ticket_get` answers short unless asked: the description's first 1,500 characters, the last 3 comments cut at 500
  (not 600: 1,500 + 3 x 600 of text left too little room under the 4,000 character bound), counts, and a `cut` line
  for every shortened field that says how much was shown and which call returns the rest. Never a silent cut.
- `ticket_list` rows are id, type, priority, status, summary (140), tags and the assignee without its title; 20 a
  page with `next_cursor`; `full: true` for the whole row.
- `ticket_update` answers id, status, priority and assignee; `ticket_comment` the entry's id and time;
  `ticket_create` the ticket's fields without its text; `ticket_close` id, status and closing summary.
- The `pilot://tickets/{id}` resource stays the whole view (`full`).

As observed (the T-277 result taken from the tape, replayed into a test portal; the method and the numbers are on
T-282): before 16,401 characters, after 4,052 by default (75 percent less). A ticket with a 20,000
character description and 40 comments of 1,000 characters: 3,958 characters by default (the test in
`tickets/portalTools.test.ts`).
