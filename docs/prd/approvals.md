# Approvals

v0.1 · built on T-2867 (PILOT-1000, slice S4 of PILOT-996) · not deployed.

## What it is

An agent sometimes needs the portal to do something it may not do itself. It asks with the Portal MCP tool `approval_request`.
A person sees the request on a card and allows or denies it. Allow runs the stored payload once, as the portal, and stores the result.
Deny stores the reason. Either way the agent gets a chat message (actor `portal:approval.<id>`).

## Rules

- **Requester.** An agent session (its own session id is recorded) or the portal itself (no session; nobody is messaged).
- **Decider.** Only a signed-in person (`actor.kind === 'user'`). An agent, a token (PAT included) or the system gets the same 404 as for a request that does not exist. There is no allow or deny MCP tool.
- **Once.** Allow claims the row with one conditional `UPDATE … WHERE status='pending' AND expires_at > now`; a second or concurrent Allow gets CONFLICT and the executor runs exactly once.
- **Expiry.** `ttl_minutes` defaults to 1440 and is clamped to 10080. An expired request cannot be allowed or denied; reads show it as `expired`.
- **Immutable.** No route or tool edits a payload; only status, decider, time and result change. (A trigger would be a non-additive migration, so the rule is in code and tested.)
- **No secrets.** A payload or reason holding a secret-shaped value, or a secret-named key (`token`, `password`, …) with a value, is refused at request time. A kind that needs a secret names it. The card masks such values again when it draws them.
- **Size.** Payload at most 4000 bytes, reason at most 500 characters; `approval_request` is rate limited (5 a minute, 30 an hour).

## Kinds

| Kind | Payload | Allow does |
| --- | --- | --- |
| `test.echo` | `{ text }` (≤ 200) | Stores `{ ok: true, output: { text } }`. For tests and trying the flow. |
| `session.bypass` | `{ sessionId }` | Enters Bypass on that session through the same gated path as the Bypass dialog (`enterBypass`): policy, capable session, fresh server code. The person's click is the acknowledgement. Audited as `bypass.entered` with `via: 'approval'` and the `approvalId`. |
| `pool.secret_set` | `{ pool (id), name, expose?, baseRevision }` | Sets one secret in a secrets pool, with the value the person types on Allow. Result `{ pool, name, revision, expose }`, never the value. |
| `jobrun.pool_env` | `{ name, args (the run's exact argv), cwd }` | Issues a one-time pass for that exact run (T-2889, below): result `{ ok: true, output: { pass, until, used } }`, no name or value. Filed by job-run.sh for a deny-listed `--pool-env` NAME; never a value. |
| `guard.refusal` | `{ tool, input (the tool input, content fields as `sha256:<hex>`), cwd, form }` | Issues a one-time pass for that exact call, as above. Filed by the rule guard for a refused call. |

### From a refusal (T-2885)

job-run.sh (a deny-listed `--pool-env` name) and the rule guard (a refused call) have no portal token, so each appends one line to `~/.claudepilot/outbox/approval.jsonl` with an id it draws itself (`apr-` and 18 hex) and prints that id in its refusal; the portal pulls the line (about every 10 s) and makes the request with that id. The line is the workspace's word, so the portal files it only when: the kind is one of these two (`APPROVAL_OUTBOX_KINDS`; never Bypass or a secret write); the session (job-run's `PILOT_SESSION_ID`, or the guard's Claude Code session mapped to its chat) is a chat of the workspace the line came from; fewer than 5 such requests wait for that session; the id is new; and the payload passes the service's own checks (schema, 4000 bytes, no secret-shaped value or key). Otherwise nothing is made and the printed id never shows (the refusal says so). A guard call too large for one line (4000 bytes) files nothing and says so. The payload is the exact call, so what a person allows is that call and nothing wider. Rejected: the portal running the command itself (the secret value would sit in an exec command line and the output could reach the agent), the hook reading the session's MCP token, and an unauthenticated route.

What is stored (T-2885 review M2): a file tool's content (`Write.content`, `Edit.old_string`/`new_string`, `NotebookEdit.new_source`, each `MultiEdit` edit) is never kept: the guard writes `sha256:<hex>` of it, and the portal digests any raw content it still finds (an old guard, a forged line, `approval_request`) before it stores the request. Every other string of a `guard.refusal` input, and its folder, goes through `chat/redact.ts`. The card shows the path and the digest.

**The one-time pass (T-2889).** Allow on either kind stores a pass: the sha256 of the exact call (kind, then for job-run the folder and every argument, for the guard the tool, the canonical JSON of the stored input and the folder; each part followed by a NUL; `approvals/pass.ts`), valid 15 minutes. The policy owner delivers the live passes of the workspace as `/etc/claudepilot/approval-passes` (root-owned, 0644; hashes and expiry only, no call). When job-run or the guard refuses a call, it hashes that call; if the file (root-owned, not group or other writable) lists it, unexpired and not in `~/.claudepilot/approval-passes-used`, the call goes through once: the hash goes to the used list, a `used` line goes to the outbox, and the portal marks the pass used and drops it from the file. job-run.sh never names the file: the read-only helper `scripts/approval-passes.sh` checks it and prints the live hashes (the T-2865 pattern; the rule guard refuses a script that names a policy file and writes, PILOT-1016). **Single use is best effort** (review m1): the used list is in the workspace's home, which the agent can write, so until the portal pulls the `used` line and redelivers the file (about 10 s), an agent that clears its used list can run the same exact call again; the window is at most the pass's 15 minutes, and only for that exact call. **A pass is per workspace** (review m2): any session of the workspace that makes the exact call (same input, same folder) can use it. It is not bound to the asking session: the session id the refusers see (`PILOT_SESSION_ID`, the hook's session) is set by the agent's own environment, so binding to it would not stop another session of the same workspace and would only add a field; the card names the asking session. A Write or Edit refusal tells the agent to put the content on its ticket, since the card shows only the path and a digest (review m3). The job-run card names every deny-listed name of the run, as one pass lets them all through (review m4). Job-run's pass skips the deny-list only; the name must still be delivered by the pool. A new pass is not a configuration change (no Restart hint). No pass on a forged line (review M1): the outbox line is the workspace's word, so Allow gives no pass for a job-run request that job-run would not refuse (the name is not on its deny-list, `JOBRUN_DENIED_GLOBS`, kept equal to `pool_denied` by a test, or the arguments do not pass it as `--pool-env`), nor for a guard request that redaction changed (it is no longer the exact call). And both refusers consult passes only on their own refusal path, so a pass for a call they allow is never used. Request lines are capped at 4000 bytes (job-run counts bytes, review M3).

`session.bypass`: an agent may ask only for its own session (`approval_request`). An admin token asks with `session_configure` `mode: bypassPermissions` (Portal MCP): the request is the portal's (no requester session), for a session the token may operate, with the token's reason or a default one naming the token; the call changes nothing else and must ask for Bypass alone. An agent principal with no session is refused there, never filed as the portal (T-2887). One pending card per session and requester (T-2887): the same asker (the same agent session, or the portal) asking again for a session whose card still waits gets that card (its first reason; no new row, no second Needs you change or push); a card that expired or was decided does not count, so the ask makes a fresh one. Another asker's card is never returned: an agent's own `approval_request` after the portal's card gets its own card, which it can read and whose outcome it is told (so at most two pending per session). Other kinds are not folded. Before the request is claimed, the person must be able to operate the session and have a fresh server code; without one the call answers `REAUTH_REQUIRED` and the request stays pending (the card asks for the code, then allows). A session that is not capable gets a stored failure (`BYPASS_NOT_CAPABLE`), nothing changes on the session. The card says in one line what Bypass does, in the Bypass dialog's words.

`pool.secret_set` (T-2867): for a protected pool (production, `[protected]`), which `pool_secret_set` refuses; its refusal names this kind, the pool id and the revision to send. An agent may ask only for a pool its workspace gets (the reach of `pool_secret_set`, a shared pool included because a person decides); any other pool is the same NOT_FOUND as a missing one. The **value path**: the person types the value on the card (a write-only field); it goes once in the `POST /:id/allow { value }` body to the executor, in memory, and from there only into the pool's encrypted store. It is never in the request row, the result, an audit row, a log or the message to the agent (tested by scanning every table). Before the claim: the person must `manage` the pool, a value must be typed, and the pool must still be at `baseRevision` (else CONFLICT; deny it and the agent asks again); each refusal leaves the request pending. An existing secret keeps its `expose` unless the payload names one. Rejected alternatives (the agent sends the value, stored encrypted; a one-shot pass for the agent) both put a protected credential in an agent's hands. A value sent with Allow for any other kind is refused.

## Tier

Every kind is tier `T2` (a person decides). The card shows the tier.

## Surfaces

- **API** (`/api/approvals`, signed in): `GET /`, `GET /:id`, `POST /:id/allow { value? }` (`value` only for `pool.secret_set`), `POST /:id/deny { reason? }`. A Deny reason that looks like a credential is refused.
- **MCP**: `approval_request { kind, payload, reason?, ttl_minutes? }`, `approval_list`, `approval_get { id }`. A session sees only its own requests.
- **Needs you**: attention kind `approval`, one item per pending request (who, kind, tier, expiry). Titles are fixed words with any agent-written name quoted and clipped; `test.echo` text never appears in one. An agent reading with scope `see` gets only the kind's label as the title. The deck's act opens `/admin/approvals/:id`; it never allows by itself (the deck rule). Web Push comes from the existing attention bridge.
- **Card** (`/admin/approvals/:id`): kind, tier, status, who asked, the agent's reason (its words, untrusted), expiry, the payload as JSON with secrets masked, the result, and Allow and Deny (44 px, phone first, light and dark). Deny takes an optional reason.
